# Tastefield — working context

Read this before changing anything. It records decisions and the reasoning behind them, so they don't get quietly undone.

## What this is

Tastefield compiles a repository's existing design system into executable context and serves it to local AI coding agents over MCP. Positioning is **coexistence, not replacement** for human sources of truth (zeroheight / Storybook / Figma): Tastefield is the active layer that makes their rules stick inside Claude Code, Codex, and Cursor.

## Non-negotiables

These exist for reasons that cost real effort to learn. Don't "fix" them.

1. **No telemetry.** Nothing is sent anywhere. Git history is not read. The original plan included selling RLHF telemetry to frontier labs — dropped, because enterprise security teams blacklist MCP servers that phone home, and the indie users who'd allow it don't generate enough volume to matter.

2. **Unknown install counts are `null`, never `0`.** Rendered as an em dash. A fabricated install figure in a pitch deck is a credibility problem. There's a test enforcing this.

3. **Never claim "100% compliance on Pass 1."** Models are stochastic; the claim is unfalsifiable and won't survive a live demo. Report measured violation-density reduction instead.

4. **Curation is not automatic.** The scheduled sweep produces a *shortlist*. Category, status, rationale and recipe membership are assigned by hand. If that becomes automatic, this is just a worse mirror of skills.sh.

5. **Skills that fail a security audit never enter a recipe.** Test-enforced.

6. **The Tailwind v3 config is detected but never executed.** Running arbitrary code from a scanned repo is a security problem and configs import plugins that won't resolve.

7. **The MCP server has no `get_everything` tool.** Progressive disclosure only. Dumping a whole design system into a context window is the failure mode this product exists to fix. **Scoped 2026-08-19, not relaxed:** this forbids a fifth *agent-facing* MCP tool that dumps the compiled corpus mid-generation. It does not forbid a *human-facing* Studio/registry ask over Tastefield's own compiled artifacts. See Vision, Remy/plugin note. **Scope of #7, clarified 2026-08-19:** this forbids a fifth *agent-facing* MCP tool that dumps the whole compiled system mid-generation. It does not forbid a *human-facing* search or navigation UI over Tastefield's own compiled artifacts (recipes, restraints, domain/category/role tags). That distinction, and the features it licenses, is logged under Vision ("Team skill plugins…") the same day.

## Architecture

```
scan(repo) → ScanResult → compile() → .tastefield/ → MCP server → agent
```

- `src/scan/` — CSS custom properties (incl. Tailwind v4 `@theme`), cva variant contracts, stack detection
- `src/compile/` — derives rules that cite the project's real tokens and components
- `src/check/` — one rule checker, shared by the MCP tool, the CLI, and the benchmark. One implementation so the claim and the measurement can't drift
- `src/mcp/` — four tools: `get_brand_standards`, `get_component_contract`, `get_design_tokens`, `check_compliance`
- `src/registry/` — skills.sh index: client, curation, discovery, momentum, snapshots, full sweep
- `src/bench/` — measures governed vs. ungoverned agent output

Rules carry a machine-checkable regex wherever expressible. A rule an agent merely reads is advisory; a rule that can be verified is enforcement.

**Restraint documentation format (2026-08-14), from tastelab.xyz.** Each negative restraint gets five fields, not a bare rule statement: Trigger (what decision prompted it), Decision (what was chosen), Reason (the logic), Evidence (specific proof — px/hex/DOM values, or the source guide citation for a real-company recipe), Trade-off (what it gives up). More rigorous than an unstructured restraint list, and directly reusable for the recipe taxonomy's Do/Don't sections.

### Determinism discipline — four principles ported from Klint (2026-08-20)

From Klint (tryklint.ai — a social-context API for agents, explicitly **not** a competitor; see Competitive landscape). Klint has no output-verification step at all, but it has the most disciplined *data-honesty* posture found across roughly a dozen products surveyed, and it is honest about the fact that its determinism lives in retrieval rather than in checking. Four principles port. Only the first is genuinely new; the other three formalize something this file already does correctly in exactly one place and should be doing everywhere.

1. **Closed vocabulary, not free text — the one new principle.** Klint's line is "every classification comes from a fixed catalog, not free text, so one label means the same thing on every post." Ported: a compiled rule must reference a canonical token/contract identifier, never a prose name for one. Two rules that mean the same thing resolve to the same identifier or they are the same rule. Without this, `check_compliance`, the agent reading the rule, and the Studio editor can each drift onto a different synonym for the same token and all three will look correct in isolation. This is test-enforceable in the same way non-negotiables #2 and #5 already are, and it is the precondition for the registry's domain/category/role tags meaning anything across recipes rather than per-recipe. None of the advisory tools in Competitive landscape (The Vibe Marketing Playbook, skilltune.dev, @skills, agentskills.me, Type) does this, because prose advice has no reason to. **Scoped 2026-08-20, because that last sentence is now too broad to defend as written.** Vibe Marketing Skills v2.1 ships 6 JSON Schema contracts (draft 2020-12, required/optional separation) governing what passes between skills — a real fixed-shape discipline, and closer to this principle than anything else in that list. It is still not this principle, for a reason worth stating rather than waving at: their schemas fix the *shape of data handed between skills*, not a canonical identifier that a rule must reference and a checker must independently resolve, and their own trade-offs section concedes there is no programmatic enforcement because the model is the only thing reading the instruction. The claim to keep is the narrow one. Nobody in that list binds a rule to a canonical identifier that something other than the model can verify, which is the half that makes `check_compliance`, the agent, and the Studio editor unable to drift apart.

2. **Evidence beside every violation, not just a verdict.** Klint ships the transcript, on-screen text with timings, and what was in frame next to each classification, so any call can be checked against source. Ported: a `check_compliance` violation always carries the offending line, the real source token it should have used, and the file and line where that token is actually defined. Not a new discipline — it is the Restraint documentation format's Evidence field above, moved from rule *authoring* to violation *reporting*, where it was previously implicit. Makes every violation self-explaining and auditable rather than an assertion, which is what the hero's pinned callouts (Landing page hero) and the scoped ask's "violation explainability" shape (Backlog) both already assume exists.

3. **Null, never a guess — extended from install counts to the checker itself.** Non-negotiable #2 already says unknown install counts are `null`, never `0`, and there is a test enforcing it. Klint applies the identical semantics across its whole surface: anything it could not establish comes back `null`, never zero and never a guess, and an untracked post is a 404 rather than a partial record. Ported: a value the checker cannot map to the extracted system returns an explicit *not in system* state — never a silent pass, and never an invented nearest match promoted to an answer. **The distinction that matters, because the hero copy sits right on top of it:** suggesting `--color-primary` for a hardcoded `#3B82F6` is fine when it is labelled a suggestion and shows its distance from the real token; substituting it silently, as though the system had answered, is the failure. This principle already has an eval scenario waiting for it in the locked task set — "an ambiguous or missing token should force a specific, checkable fallback rather than an invented value" (What is NOT done, from Little Plains) — written before the principle had a name.

4. **One machine-fetchable rules contract per repo.** Klint's docs are built for machine consumption: append `.md` to any page for raw markdown, `/llms.txt` indexes the site, "the entire contract sits on one page an agent can fetch in a single request," and errors name the fix rather than just the failure. Ported: a single fetchable rules contract per repo that both the coding agent and `check_compliance` read, so the rules the agent was given and the rules it is graded against cannot diverge. **Reconciled against non-negotiable #7 before anyone reads this as a `get_everything` in disguise:** the contract is a setup-time artifact and the checker's input, not a fifth agent-facing MCP tool that dumps the compiled corpus mid-generation. That is the same scope line already drawn on 2026-08-19 for the human-facing Studio ask, applied unchanged. Progressive disclosure still governs what the agent pulls *during* generation.

## Two axes, deliberately not merged

- `domain` — what a skill is **about**: visual, brand, copy, motion, architecture, content, conversion, process
- `category` — what kind of **rule** it compiles into: structure, boundary, voice, motion, process

Skills are frequently multi-domain and must not be forced into one bucket.

Brand and copy matter more over time than visual rules. Base models keep getting better at spacing and colour on their own; they will never independently know that a company can't say "cheap" or can't use red on a checkout button for compliance reasons.

**"Add engineers as an axis" — answered 2026-08-19 by not adding one, because it's a category error worth naming precisely.** The domain axis describes what a rule is *about*, never who holds it. "Engineers" is an audience, not a domain, and engineering judgment already has a home on the existing list: **architecture**, defined as composition rules (how components combine into patterns and templates) and behavioral contracts (navigation logic, action placement, validation timing) — sourced from a real enterprise design lead, already given concrete content, currently deferred only by build order. Adding an "engineering" domain next to architecture would duplicate it, and the audience question belongs in Open questions where it now lives, not in this taxonomy.

**Design engineers specifically: already considered and declined as a role recipe, for a reason the pivot makes stronger rather than weaker.** The 2026-08-15 declination stands — a design engineer isn't *adjacent to* the system the way a creative director or social-media manager is, so there's no extra layer of judgment to wrap; they are the primary user of category recipes, Studio, and `check_compliance` directly. That is exactly why the engineer half needs no new axis: the product as built today *is* the engineer-facing product. What the blurring observation actually identifies is not a missing role but the **bridge persona** — the design engineer sits on the seam between the token half (built) and the brand/copy half (written but unbuilt), and is the one person who needs both in a single session. Two independent sources already in this file confirm the seam is real rather than a trend observation: the enterprise design lead's "a token file doesn't tell the agent that our Wizard consists of a Top Bar, Stepper…" and Little Plains moving all behavioral work out of Figma into code-based prototyping labs.

**The unifying line, and it's the tasteful way to broaden: the customer is whoever owns rules an AI keeps violating.** Not "for creatives," not "for design systems." An engineer owns component contracts, token usage, composition rules, behavioral contracts; a creative owns voice, banned phrases, motion feel, brand restraints. Same mechanism — compile the decisions, serve them to the agent, verify the output — different domain on a list that already has room for both. This phrasing is deliberately self-limiting, which is the point: if someone owns no rules an agent can violate, they are not the customer, which excludes the sales trainer, the general knowledge worker, and the whole "skills for everyone" catalog lane in one test rather than needing a new prohibition. Candidate replacement for the over-indexed "What this is" opening line (see Open questions, audience) — neither "repository" nor "design system" survives contact with it.

**Architecture's deferral is the specific thing to revisit, and it may be cheaper than assumed.** Composition rules and behavioral contracts look softer than tokens but are substantially machine-checkable — a required child in a component tree, an action in the wrong container, validation firing after navigation instead of before — and they reuse `src/scan/`'s existing cva/AST parsing rather than needing a new editor paradigm the way Copy does. That combination (deterministic, existing infrastructure, the one layer tokens provably can't reach, serves the engineer half of the audience) makes it a stronger candidate than its current "genuinely deferred" status implies. Proposed order if the audience broadens both ways: Copy first (cheapest, unlocks the role recipes), Architecture second (engineer half, deterministic, reuses the scanner), Visual/Motion stay where they are since they're partly built. Not decided — build order lives under Competitive-pressure reprioritization.

**Distribution is already engineer-native, which is an asset for creative content rather than a conflict.** The whole delivery layer — `SKILL.md`, MCP, `npx`, Claude Code / Cursor / Codex / opencode, `~/.claude/skills/` — is developer-shaped, and that stays true no matter how creative the *content* is: a `social-media-manager` recipe still installs on engineer rails. The non-developer surface for the same compiled rules already has a home in Vision as the seventh consumption point (ambient, workplace-embedded agents — Grok Bot in Slack, Type). Engineer-native rails now, ambient surfaces later; no third thing to invent.

## Vision — beyond code (not built, not roadmapped as a phase)

Today Tastefield only governs code — the AI writing components inside an IDE. The longer bet: as AI starts generating more than code (marketing graphics, social assets, ad copy), something has to keep all of that on-brand too, not just the codebase. Working name: **Creative & Brand Intelligence** — extends Taste DNA (tokens, negative restraints, voice rules) to any AI generating any output for a company, not just a coding agent in Cursor.

Further out: a multi-agent setup where specialist AIs (a design agent, a dev agent, a review agent) transact with each other autonomously to complete a task end-to-end — an "agent economy" for design and dev work. Tastefield's role doesn't change in kind if that happens: it's still the layer making sure whatever comes out — regardless of which agent produced it, or how many agents the task passed through — matches the company's actual brand rather than generic AI output.

Sharpened further, 2026-08-14: this has a concrete buyer — one creative director directing a fleet of specialist agents instead of a team of people. More agents involved means more drift risk, not less, since nothing naturally keeps their outputs coordinated the way a human team stays aligned through meetings and shared context. The director is the person this vision was previously missing. Tastefield's role stays disciplined either way: govern whatever's dispatching the fleet, don't try to build the dispatching itself — same "coexistence, not replacement" posture already applied to zeroheight and Figma, applied here to whatever ends up doing agent orchestration.

Sharpened 2026-08-14, against Aura.build's creator marketplace: every marketplace model looked at so far (skills.sh Packs, Aura's template library, the Taste Arena idea below) is a human creator economy with AI in the middle — humans make things, humans browse and buy, AI just generates. The actual differentiation is a registry an agent can transact with directly: querying variants mid-task, paying for one via the x402 idea (see Roadmap reframe proposal), with no human browsing step in between. Creators don't have to be human-only either — an agent that authors a well-performing recipe variant could submit and rank on the same leaderboard as human-authored ones. The structural edge already available: Tastefield lives inside the agent's own tool-use loop via MCP; a marketplace a human has to browse and copy from isn't.

Made concrete 2026-08-14: Higgsfield already ships a live MCP server (mcp.higgsfield.ai) that works inside Claude Code and Cursor — the same environment Tastefield's own MCP server lives in. A single agent session could have both connected: Tastefield supplying brand rules (colors, motion pacing, logo placement, voice), Higgsfield generating the actual video, image, or ad. No generation infrastructure to build — Higgsfield already solved that at scale (25M+ users, 30-50+ aggregated models including Sora/Veo/Kling, direct enterprise sales to brands and agencies with IP indemnification). Tastefield's job stays exactly what it already is: compile and serve rules, not generate content. Real evidence this gap exists today, not hypothetically: Higgsfield's own published example prompt for building a website hand-types brand constraints into natural language ("celadon sage, warm ivory, pine ink, Cabinet Grotesk and Inter Tight, one red accent") because there's no structured alternative — the same "AI wasn't in the meeting where the rules got decided" problem this file opens with, just showing up as a human typing color names into a prompt instead of a hardcoded class.

The generalizable version, not a video-specific one: the actual product decision is one generalized brand-rules MCP tool — voice, restraints, motion, not just code tokens — that any MCP-compatible generator can read from, the same way Higgsfield says any MCP client can connect to them. Video, ads (Higgsfield's own Marketing Studio and UGC factory), and website-building (Higgsfield's own skill category, and Toolcraft from the very first strategy session) are three consumption points for that one tool, not three integrations to build separately. Resist chasing each generation category individually — the leverage is in the one generalized tool, not bespoke work per vendor.

Fourth consumption point, confirmed 2026-08-14: Motion (motion.so), an MCP/API-callable launch-video and motion-graphics agent, has a literal, named "Design system" slot in its own prompt UI, alongside Connectors, uploaded assets, and style references — a concrete, already-existing hook to point the generalized tool at, not a hypothetical one. Its "Research" step currently re-derives brand colors and type from a live site read on every run rather than a curated source — the same guess-from-scratch gap already found in Higgsfield's LOOMERE example, now confirmed twice independently rather than once.

Fifth consumption point, confirmed 2026-08-15: Hyperagent — a real, polished agent-orchestration platform shipping a named fleet (creative director, social media manager, podcast producer, editor) that researches, builds, and delivers real work. No visible brand-governance layer on any of it. Different in kind from the first four (a fleet-management platform, not a single generator), but the same underlying relationship: its agents are a plausible reader of the generalized brand-rules tool, same as Higgsfield and Motion. Also the clearest evidence yet that building an owned, competing agent fleet is a real, separate bet from building the rules engine — see the staged phasing below.

Sixth consumption point, confirmed 2026-08-15: GetLayers — a curated design-asset library (templates, 3D scenes, backgrounds) shipped as a real MCP server, with one capability closer to Tastefield's own scan-first pattern than anything found so far: "point it at your repo, it reads your code first, then proposes where a scene or motion belongs." A live tool reading an actual codebase before generating, not just a live site or uploaded context. Worth being precise about the difference, though, since it's not just another peer: GetLayers reads the repo for *placement* — does this look right sitting here — not for *brand fit*. Its whole value proposition is bringing its own curated aesthetic to a project; Tastefield's is extracting and enforcing a project's own. Nearly opposite directions on the same axis. Run ungoverned on a real brand, GetLayers' repo-aware feature has no mechanism stopping it from injecting a coherent-looking but completely off-brand aesthetic — a live illustration of exactly the risk `check_compliance` exists to catch, not just a hypothetical one.

Seventh consumption point, confirmed 2026-08-15, a genuinely different shape from the first six: ambient, workplace-embedded agents, not generation destinations. Grok Bot (xAI + Cursor, public beta since 2026-08-11 — six days old, launched following SpaceX's $60B acquisition of Anysphere, Cursor's own parent company, notable since Cursor is one of the three primary MCP clients already named in "What this is") already ships one-click plugin connections — Context7 shown as a live example in their own product — alongside custom plugin building, automatically choosing plugin (faster, reliable) over raw browser control depending on the task. A Tastefield connection is exactly the shape of thing that plugin panel already accommodates. Real use, not hypothetical: on-brand copy drafted directly in a Slack thread (Copy domain, marketing-director/social-media-manager role recipes, just triggered conversationally instead of through a build pipeline), or ambient checking — a design link dropped in a channel, `check_compliance` flags it passively rather than only at commit time. Worth naming as its own category: not a destination you go to generate something, but tasks handled wherever a team already talks. Gartner's cited projection — 40% of enterprise apps embedding task-specific agents by end of 2026 — is real signal this is a major, current category, not a niche one.

Second confirmation of this same category, 2026-08-15: Type (type.com) — a shared team workspace on top of existing Claude/Codex subscriptions, built by a team with real pedigree (Airbnb, Atlassian, Meta, Stripe, X), department-templated Spaces (Marketing, Product & Engineering, Support, Sales, Data, HR/Ops) pre-wired to real tools. "Best in class Slack integration — mention agents, route access by channel" is the identical shape as Grok Bot's, for Claude/Codex instead — two independently-built products converging on the same pattern within days of each other, stronger evidence than either alone. Their Marketing Space ("suggests content, improves ads, and monitors competitors") is real, described validation of the `marketing-director` role recipe, landing right after it was named. Not a governance competitor — nothing here touches design systems or brand compliance.

  **Sharpened 2026-08-19: Type is genuinely multiplayer, and the cost of that is a destination.** Slack is their side door into a hosted workspace. Tastefield's delivery layer is already engineer-native (MCP, `npx`, Claude Code / Cursor / Codex) and ambient surfaces are already the seventh consumption point, not the primary one. Building a second hosted team workspace to match Type/Hyperagent would undercut that, not extend it. Shared state is a repo those harnesses already read and write; there is no side door because there was never a separate front door. Five harness-native multiplayer shapes, and the "Studio is not multiplayer today" gap, are logged under the Remy note below — do not invent presence/co-editing in Studio to close it.

Pattern-level finding, now confirmed four times independently, worth stating plainly rather than as a single observation: Type's own pitch — "self-learning, shared memory... self-improving, reviews its own work and improves with time" — is the identical advisory-accumulation shape already found in the Vibe Marketing Playbook's Brand Memory, skilltune's eval scoring, and @skills' AI Boost rating. Four different, unrelated companies, all building "gets better through use," none building deterministic verification against a specific rule.

Open technical question, not assumed to work: `check_compliance` verifies code deterministically — a regex catches a hardcoded hex value with certainty. Verifying whether a generated video frame or ad image actually matches brand rules is a fuzzier, likely computer-vision-based problem — a real capability gap, not a natural extension of what's built.

Sharpened 2026-08-14 — the mission stated plainly, using the framing that prompted this: "the brand Swiss Army knife." Not "Tastefield does everything a creative director or agency could do" — a creative director's replaceable work is production, increasingly already handled by Higgsfield, Motion, and Toolcraft. Their irreplaceable work is judgment: does this match the brand, regardless of who or what made it. A Swiss Army knife isn't valuable because it replaces a table saw — it's valuable because it's the one small, sharp thing that's useful everywhere. That's the correct shape here: not a bigger tool that does more, but the same one — brand judgment — showing up in more places: code, video, ads, websites, motion graphics, via the one generalized brand-rules tool above. Building the production side back in would undo the discipline the rest of this section already argues for.

**Phasing for the vertical creative-director ambition (2026-08-15).** Split by what costs engineering time versus what costs conversation time, since those don't have to be sequenced against each other:

- **Stage 0, now, parallel with Phase 1.** Structured domain research, not casual conversations: interview or shadow 5-10 real creative directors/agency leads, spread across the registry's existing categories (fintech, consumer, SaaS, devtool, healthcare) for coverage. Capture where they actually intervene or reject work and why, how they defend a brand decision to a client, what triggers a real revision cycle vs. noise, what's tedious vs. needs real judgment. Write findings directly in the Trigger/Decision/Reason/Evidence/Trade-off format already adopted — usable immediately as sourced restraint content for near-term registry recipes, not just background research for later. Pays off even if Stage 3 never happens. Compensate people properly for their time. Explicit pipeline, 2026-08-15: these interviewees are the natural first creators for the registry's new "Recipes by role" section specifically — a creative director interviewed for Stage 0 research is the obvious first author of the actual `creative-director` recipe, not just a source quoted inside it.

  **Allocation principle, 2026-08-15: spend interview time only where a research-and-synthesize workflow can't reach.** Real pattern already in practice elsewhere: research a domain via Perplexity, feed it to Claude Code, generate a skill from published theory (classic copywriters, modern DTC principles), refine by testing against real outputs — fast, and genuinely good at capturing published, generalizable theory. It cannot reach the thing Stage 0 exists for: not general theory, but the undocumented, situational judgment that only exists in one person's head — why a specific creative director rejected a specific piece of work, the pattern behind that call. Directly relevant to the risk already logged above: the whole Stage 0→2→3 chain assumes tacit judgment converts into generalizable rules; capturing only the theory layer gets the easy 80% and misses the point. Also sharpens, not undermines, the earlier @skills finding — a workflow like this crowds the generic hand-authored lane further, making Stage 0's real-sourced content matter more, not less. Practical rule: don't spend scarce interview time on ground a research-and-synthesize loop already covers well; reserve it for the reject/approve reasoning and client-defense patterns nothing published captures.

  **Capture guidance, 2026-08-15, from "Design Is How It Tastes" (see Studio, DESIGN.md critique): preserve encounter-language, don't compress it into tokens too early.** If a real creative director's actual reasoning is closer to "this feels like it's trying too hard" than "the padding's wrong," write down what they actually said, not an immediate translation into token-speak. Deepens the same differentiation the allocation principle above protects — real, sourced, embodied reasoning is exactly the "compiled history with real corrections" already named as one of the four things that resist fast-following, and compressing it early loses the same signal the essay describes losing from design specs generally.

  **Public delivery mechanism, 2026-08-15: a podcast, "General Creativity."** Not a separate idea from the research above — the same Stage 0 interviews, recorded and released, doing the research and building audience from one effort instead of two. First guest deliberately chosen: someone excellent at podcast production, interviewed about podcasting — direct-sourced material for the podcast-producer role recipe's Phase A (sonic branding, mastering, show-notes voice), not just a good opener. Same scope caution as Machinekind: stays a strength if it tracks Stage 0's actual research cadence; becomes a liability if it grows into its own production commitment independent of that.

  **Priority against the marketing site, and where it lives, resolved 2026-08-15.** The marketing site comes first, clearly: the actual moat is real accumulated customer use — real compiled histories, real corrections — and the site is the direct path to converting interest in the already-working Phase 1a into that real usage. The podcast produces research and incidental reputation, both real, but reputation is a slower, longer-horizon asset than real customers using a real product, and it doesn't itself generate the thing just identified as durable. Site placement follows the same test as the scope caution above, made explicit: if the podcast stays tied to Stage 0's original purpose — real creative directors and agency leads, sourcing real recipe content — it belongs close to Tastefield, linked directly from the site, legibly Tastefield's own research happening in public. If it grows into "any skilled knowledge worker learning about creativity broadly," that's the same "medium empire" risk already flagged for Machinekind, just relabeled — a real, different, bigger project that would dilute Tastefield's own positioning rather than support it. Default: scoped and integrated now, standalone only as a deliberate later decision if Stage 0's research genuinely outgrows what the site can hold — not assumed upfront because the bigger version sounds exciting.
- **Stage 1, already in motion.** Prove the rules engine — Phase 1 finished, Machinekind as the real-world proof it works.
- **Stage 2, built on Stage 0 + Stage 1.** Role-specific recipes (creative-director, social-media-manager, podcast-producer — the taxonomy extension proposed 2026-08-15), now backed by real domain research instead of a plausible guess.
- **Stage 3, only once 1 and 2 are proven and demand is validated — deliberately last, still unphased.** An owned creative-director agent, differentiated by native compliance built into the generation loop rather than a rules file a third-party agent might or might not read closely — the edge identified against Hyperagent. Competing with Hyperagent directly isn't ruled out here — it's sequenced, not rejected.

  **Design discipline required if this proceeds, 2026-08-15: no bundled proprietary recipe.** An owned agent shipping with its own free, in-house `creative-director` recipe cannibalizes the marketplace directly — nobody buys a creator's version when the default is free and comes from the platform itself, undercutting the trust the Bradley-Terry blind-voting system exists to protect. The owned agent must source its default recipe from the same open leaderboard everyone else competes on — winner of the public vote gets the slot, Tastefield's own entries included and not identity-protected any differently than anyone else's. Turns the conflict of interest into a public demonstration the marketplace actually works, rather than a reason to distrust it.

  **Real cost, worth deciding with eyes open: this converts Hyperagent from partner to competitor.** Hyperagent is logged in this section as a confirmed consumption point for the generalized brand-rules tool — a fleet whose agents would read Tastefield's rules. An owned creative-director agent goes head-to-head with Hyperagent's own instead. Higgsfield and Motion are mostly unaffected — generation infrastructure, not orchestration, a different category — but Hyperagent specifically loses partner status if Stage 3 happens. Not a reason to avoid it; a cost that shouldn't be discovered after the fact.

**Adjacent bet, not a new consumption point: turning any archive into an agent tool (2026-08-18, from a startup-ideas video segment, "Expert Archive to Agent Tool").** A different pattern than the seven consumption points above — instead of a generator reading Tastefield's rules, the archive itself becomes the compiled thing. The pitch: pick an expert with a deep archive and a narrow audience, transcribe/tag it, ship one job-specific workflow (paste X, get a cited, scored, structured Y), monetize per-use rather than via ads. Whether this belongs inside Tastefield turns on one filter, not enthusiasm for the pattern: the domain axis. A sales trainer's or real-estate expert's archive isn't visual/brand/copy/motion/architecture/content/conversion/process — building it inside Tastefield would be exactly the "widen the category, become a worse mirror of skills.sh" failure mode non-negotiable #4 and the Taskmarket domain-axis discipline (Roadmap reframe, below) both already warn against; it's a separate product on a shared, licensable engine (scan → compile → check → MCP), not a Tastefield feature. A design/brand/copy/motion/conversion creative's archive is different — already inside the existing domain taxonomy, and "populating the copy/content/conversion side of the existing axes" is already the named gap, not new scope. But even there, check the buyer before the domain: Tastefield's core product is defensive (you have a system, stop AI from drifting off it); this pattern is generative (you have no taste, you're importing someone else's) — the identical opposite-direction-on-the-same-axis relationship already drawn against GetLayers above. Concretely: hostable in the Public registry as a distinct "guest recipe" subtype (see recipe taxonomy below), never silently merged into the "extract and enforce your own system" recipes it sits next to.

  **Monetization pattern, same source.** The archive's raw content is usually already free (a YouTube video costs nothing to watch) — what's actually sold is the compiled, tagged, cited judgment layer on top of it, the same reason brand/copy rules were already said to outlast visual ones ("Two axes," above: base models won't independently know a company can't say "cheap"). Two different buyers need two different pricing shapes: an occasional human user wants a single metered result, not a subscription; a downstream builder or agent wholesaling the expert's judgment into its own product is the real x402 case (Roadmap reframe, below) — an autonomous caller with a budget, not a human filling out a checkout form.

  **What actually to build if this proceeds — Little Plains as a worked example of the same pattern, 2026-08-19.** Their essay is not a competitor note; it is this bet shipping in the wild: years of Gin Lane + Little Plains material ("dead stock") compiled into a knowledge layer, then a first product on top. Steal the compile discipline, not the product they built (visual search / chat / voice over a studio archive). Eight steps they would repeat, mapped onto Tastefield's already-named guest-recipe shape:

  1. **Name the job before the archive.** Their first question was "What can Little Plains do? What has Little Plains done?" For a guest recipe the equivalent is one workflow, not a knowledge center: paste an ad / caption / frame, get this named expert's cited, scored, structured review. Chat-with-the-archive is the failure mode they already hit ("useful organizational knowledge requires editorial judgment... otherwise a chatbot that will confidently make up our own history"). Matches the video's "paste X, get a cited, scored, structured Y" exactly. Do not ship a fourth MCP tool that dumps the transcript corpus.

  2. **Organized and usable are different projects.** Transcribing Stage 0 interviews, podcasts, or an expert's YouTube is recovery, not a product. Their second pass was translation: sources ingested and normalized, public vs private split, indexed in the shape the product would actually query. For Tastefield that shape already exists — Trigger / Decision / Reason / Evidence / Trade-off restraints, not embeddings. A transcript can preserve a whole session and bury the one reject that mattered; the Evidence field is where that reject has to land, in the expert's encounter-language, not a generated summary sitting between the source and the recipe (their rule: "no generative summary sits between the original and the index"). Directly compatible with non-negotiable #4 and Stage 0's capture guidance.

  3. **Write the fast layer by hand first. Do this before touching retrieval.** They called four to six documents (who we are, how we work, what people always ask, how the agent should behave) "the single most valuable part of the whole project." A guest recipe's fast layer is the compiled restraint pack the MCP already knows how to serve — `get_brand_standards` / voice / motion rules for that expert — versioned, human-approved, only changing when the expert or a curator publishes an update. The full interview/podcast/YouTube corpus is deep knowledge: worth searching later if a question needs research, not what an agent should pull on every `check_compliance` call. Shipping embeddings, visual similarity, or "chat with this critic's archive" before the fast pack exists is repeating their expensive first mistake.

  4. **Render the review deterministically where possible.** Their project fact sheets are "rendered directly from approved Sanity fields... a model doesn't write the above." Same split Tastefield already has: regex-checkable rules go through `check_compliance` (off-palette hex, banned phrase, missing confirmation); judgment-shaped calls stay structured fields the expert already approved (score, cited restraint, suggested revision), not a model improvising in that expert's voice on every request. Carry a source digest on the compiled recipe so a change in the underlying archive (new interview, corrected restraint) is detectable — same mechanism just added for `.tastefield/` snapshots, applied to a guest recipe instead of a customer's repo.

  5. **Keep the expert in the publishing loop.** "A model proposes line-level changes, and a human accepts, rejects, or rewrites. Publication creates immutable versions. Nothing said in a meeting quietly becomes public truth." Stage 0 already named interviewees as the first authors of role recipes; a guest recipe is the same loop with the expert's name on the artifact. Private workshop notes stay private. Public talks / approved quotes become Evidence. The expert is the publisher, not a source the pipeline scrapes.

  6. **One intent, one path — and show artifacts first.** They split Explore / Ask / Voice because one catch-all query made common answers slow and hard answers shallow; they also warn that a chat-first empty input "asks visitors to know what they want before they've seen anything." For the registry: the guest-recipe page shows specimens of that expert's actual judgments (the human-browsable half already specced — mood caption, visual specimen, now also a few cited reject/approve examples). The agent-fetchable half is the one job (`npx --recipe=` or a hosted, metered `review` call), not a chatbot. Public browse stays free; the compiled pack is what Paid gates — already decided, just named here as the archive product's surface rather than a generic recipe's.

  **What not to copy from Little Plains, stated so it doesn't sneak in as scope.** Their image-embedding pipeline, masonry visual search, OmniBar, and voice stack are a studio-site retrieval product. Tastefield's wedge is still compile + check, not search. Building "our own dead-stock explorer" would be a second company on a shared metaphor. Also keep the domain filter already written above: a creative director's / copy critic's / motion designer's archive can become a guest recipe; a sales trainer's cannot.

  **Smallest buildable slice, if this ever leaves vision.** One Stage 0 creative-director interview (already planned, already compensated), originals preserved, four-to-six restraints compiled by hand into a named guest recipe, one paste-in → scored-and-cited review served over the existing MCP tools, expert approves before publish. No new scanner, no embeddings, no hosted API required for the local path. The hosted/metered path is the same Open-questions fork already on the Hosted Recipe API / x402 — don't invent a third payment surface for archives. Sequencing unchanged: real category/role registry content first, guest recipes after, per the taxonomy note below.

**"Paste any link, auto-publish a recipe" proposal, 2026-08-19, from BibiGPT — validates the mechanic, doesn't relax the guardrails.** BibiGPT (bibigpt.co, 1M+ users, already indexed on skills.sh as `JimmyLv/bibigpt-skill`) is real, proven-viral evidence for half of this: paste a YouTube/Bilibili/podcast/article link, get a structured artifact (timestamped summary, transcript, mindmap) in ~30 seconds, free tier converting to Plus/Pro, distributed via web + browser extension + desktop + mobile + its own MCP endpoint. Good confirmation that "paste something, watch structure appear" is a real growth loop — the same instinct already behind the Specimen Wall's "paste `stripe.com`" hero. But BibiGPT itself stops at summary/transcript/mindmap — a human-readable artifact, not a compiled rule or an executable skill. It never crosses into judgment or enforcement; it's advisory in the same sense as every other tool in this section, just for video instead of design tokens. The proposed extension — auto-extract *and auto-publish* "a recipe of skills" from an arbitrary pasted link — is not a new idea, it's this file's own archive-to-agent-tool bet (above) with three already-decided guardrails removed at once: no domain filter (any topic, not just visual/brand/copy/motion/architecture/content/conversion/process — the exact "sales trainer's archive" case already ruled out), no human curation (non-negotiable #4 exists specifically to prevent auto-published listings), and no expert-in-the-publishing-loop (guest-recipe rule 5, above — plus a real consent/rights problem distinct from the design ones: turning someone's YouTube talk into a monetized listing without them approving it, not just an engineering shortcut). Auto-publishing to the same marketplace as compiled recipes also reopens the exact problem just logged against agentskills.me two entries above — a flood of generic, unverified listings undermines the differentiation the registry is supposed to have, it doesn't build it.

  **Where this is actually a good idea, reframed rather than rejected.** The parsing-difficulty read is correct and worth taking at face value: transcribing/summarizing a link is genuinely much cheaper to build than `src/scan/`'s CSS/cva extraction or sandboxed component rendering. Two legitimate, already-compatible homes for it, neither requiring a new roadmap phase: (1) an accelerant for the Stage 0 / "General Creativity" podcast pipeline already planned — feed it Tastefield's own interviews and podcast episodes first, content it already has rights to, producing draft Trigger/Decision/Reason/Evidence/Trade-off restraints for a human (the interviewee) to approve — this is just a faster version of the "smallest buildable slice" already scoped just above, not a new feature; (2) a free, public, top-of-funnel utility in the same spirit as the Specimen Wall, scoped to design/brand/copy/motion content (a creative-director talk, a copywriting teardown) — output is always a draft a human reviews before anything touches the registry, never an auto-publish button. Keep "viral utility" and "marketplace listing" as two different states of the same object, gated by the same publish step Studio already has (DRAFT → Publish), not two names for the same button.

**A second adjacent pattern, distinct from both the seven consumption points and the archive-to-agent-tool bet above, 2026-08-19: an upstream 0-to-1 generator as an onboarding source, not a consumption point.** OJO (ojo.art, see Competitive landscape) generates a brand-new product from a prompt, then exports to Figma or hands off to Codex/Cursor/Claude Code/Kimi for implementation. Nothing about that flow reads Tastefield's rules at generation time — the opposite relationship from Higgsfield, Motion, Hyperagent, and GetLayers, which all consume the generalized brand-rules tool mid-generation. What OJO's export step actually produces is an ordinary repo landing in Cursor or Claude Code — exactly what `src/scan/`'s existing Local source connection (see Studio) already reads, no new capability required. The only real work here is messaging, not engineering: explicit "import from OJO/Figma export" onboarding, framed as "OJO gets you to v1; Tastefield keeps every AI-generated commit after that on-brand" — logged as a backlog item below, not a roadmap phase, since it costs a sentence of copy, not a build.

**A third adjacent pattern, 2026-08-19, from Remy / Greg Isenberg ([How to Use Claude Code Skills and Plugins with Your Team](https://www.youtube.com/watch?v=xHsftiyT9pQ&list=PLQHTakJAwGLMQxKVlKUVpC7aiYTZ2j2J9)): team-skill distribution, not a new product category.** Core claim: skills are SOPs packaged as markdown; the unlock isn't writing them, it's *distributing and versioning them across a team* so they don't die on one laptop. His mechanism: dump skills into a GitHub repo, expose it as a Claude Code / Codex **plugin marketplace** (`/plugin` → add marketplace → paste repo URL), everyone installs with auto-update on, version control makes a bad edit revertible. He also showed a UI over the repo (skill-relationship graph, an "ask" search, a usage-tally hook per teammate) and a "self-improvement loop" block appended to every skill that proposes one edit after each run. Claude Enterprise can bake org plugins into every seat so non-technical teammates never open a terminal. His personal vs. team split (a private sandbox repo plus a company-owned org repo) is the same ownership argument already made for compiled recipes living in a GitHub org rather than on an employee's machine.

  **What this only validates, not new information.** Plugin-as-bundle (skills + MCPs + hooks) is close to the recipe concept and to Vercel Packs already logged under Registry facts ("treat as a window, not a moat"). Usage-driven trust is the Arena's usage leaderboard. "Corrections become candidate rules, human approves" is the Adobe-differentiation mechanic, now independently described a further time. His backup-loss story (Claude deleted a local folder of ~150 skills, no backup) is vivid supporting evidence for the already-decided split between anonymous local scanning and an authenticated Publish step (Hosted Recipe API open question) — persistence is a real user fear, not just a security abstraction.

  **What's genuinely new, three things.** (1) Native harness plugin marketplaces, including org-wide enterprise rollout with zero terminal use — different from Vercel Packs; it's Anthropic's first-party primitive. A real gap in the current distribution list (`npx`/MCP, shadcn-CLI, @skills — all developer-shaped). Cleanest answer yet to the audience question: if a marketer owns the rules, they shouldn't need `npx`. Concretely: publish the registry as a Tastefield plugin marketplace *alongside* `npx --recipe=` — same content, a channel that reaches the non-technical half of "whoever owns rules an AI keeps violating." Packaging, not new engineering. (2) A hook that tallies skill usage per person — a concrete implementation for the already-proposed, unbuilt usage leaderboard (Context7 Rankings-style). Right now that's a good idea with no mechanism; this is the mechanism. Opt-in and anonymized, identical shape to the coverage-gap bounty signal under non-negotiable #1. (3) A self-improvement block at the bottom of every skill file ("did a step fail, did the user correct you, propose one change") — a literal UX pattern for turning "a creative director rejected output and said why" from a manual process into something that happens at the end of every session, surfacing a candidate restraint for human review, never auto-merging (stays inside non-negotiable #4). Steal: append this block to every compiled recipe export.

  **Near-term leverage, three items, cheapest first — not a funding-order change.** (1) Self-improvement block on every compiled recipe export — zero new infrastructure, strengthens the "corrections compound" line against Adobe/Blume, ships with funding-order step 1 (catalog + checker). (2) Plugin-marketplace as a seventh distribution channel — packaging work, opens the non-technical buyer without committing the still-open "creatives are the primary audience" question. (3) Usage-tally hook feeding the Arena usage leaderboard — gives that already-designed mechanic something real on day one of the registry, instead of waiting for Phase 4. All three sit in Backlog; none leave their existing phase slots.

  **Guardrails that still hold.** Plugin-marketplace distribution is a channel, not permission to skip curation — every plugin published still clears non-negotiable #4; auto-update propagates an *approved* change. The usage hook is opt-in/anonymized only. Do not become a generic cross-harness skill/hook manager — that is Blume Sidecar's actual product (Competitive landscape).

  **Skills assistant, resolved 2026-08-19 rather than declined.** A first-pass read treated Remy's "ask what to run next" UI as the `get_everything` failure mode and as Blume's territory. That conflated two surfaces. Non-negotiable #7 constrains *agent-facing retrieval during generation* — don't add a fifth MCP tool that dumps the compiled system mid-task. Remy's assistant is a *human-facing search/navigation UI* used *between* tasks, over a corpus he already owns. Blume's lane is *generic, cross-harness* — whatever rules/skills/hooks/agent-files exist across Cursor, Claude Code, Codex, omp, Pi, for any purpose. An ask that only answers questions about Tastefield's own compiled, curated corpus (recipes, restraints, domain/category/role tags, Trigger/Decision/Reason/Evidence/Trade-off records) never becomes that. **The dividing line, stated as a rule:** an ask feature is in bounds if (a) it is a human-facing Studio/registry surface, never a fifth MCP tool, and (b) its corpus is bounded to Tastefield's own compiled artifacts, never a general skills/rules/hooks index. The moment either line is crossed — "index my Cursor rules too" or "let the agent call `ask_anything()` instead of `get_component_contract()`" — it is the thing #7 and the Blume comparison correctly forbid.

  **Five features inside that boundary, none of them a new knowledge base.** (1) **"Which recipe fits this"** — natural-language front door to the registry. The mood-caption picker already lets someone browse by vibe; an ask box is the same lookup accepting "I'm building a fintech onboarding flow" and returning `fintech-trust-first/neobank` plus the restraints that would fire. Index over metadata that already exists. (2) **Reverse-lookup explainability on `check_compliance` violations.** When a rule fires, a human asks "why" and gets back the one restraint plus its Evidence citation — progressive disclosure applied to a human, not a competing feature next to #7. Citable line if it ever sits on the marketing site: "ask why, get the one rule that fired." (3) **"What's next" for role-recipe sequencing.** Podcast-producer already has a Phase A/B split; marketing-director already bundles four domains. "I just filled in Copy, what's the highest-leverage domain to add next" reads the same domain-tagging metadata Studio's right rail already generates from. (4) **Recipe-dependency graph as a Studio visualization, not a chat.** Maps onto "you author skills, you publish a recipe" — show which skills a role recipe assembles. Visualization of data the domain multi-select already requires. **Scoped the same day: one recipe's `runs:` status board, never a Skill Atlas of the catalog** (see decline note below). (5) **A scoped front-end for the self-generating bounty signals, once the Arena exists.** "Show me what's missing" over exactly the three already-designed signal types (taxonomy gap, coverage gap, weak/stale recipe). Correctly sequenced behind the Arena; a better UI for an approved mechanism, not new scope.

  **Skill chaining, 2026-08-19 — Remy's weakest on-screen bit, and the one Tastefield can make real.** A Claude Code/Codex "skill chain" is not a runtime. An orchestrator `SKILL.md` names other skills and tells the agent what order to run them in; the agent follows that the way it follows any other instruction. No engine enforces the sequence, no typed handoff, nothing stops a skipped step or a hallucinated intermediate. Remy's own rule for chaining versus one fat skill was reusability — chain it if you'd ever want a sub-step alone. What he demoed was a static call-graph plus a chatbot recommending what to run next: nothing to watch happen.

  **The feature is a verified chain, not a better diagram.** Every other chain in this landscape (his, agentcn's, @skills', Vercel Packs) is advisory sequencing. Tastefield already has the missing piece: `check_compliance` is deterministic. Shape: (1) a role recipe declares an ordered `runs:` list of sub-recipes — same metadata family as domain tagging, already required for the right rail; (2) each stage's output is checked against *that stage's own* compiled rules before the next stage's context is served over MCP — the difference between "the instructions said Copy then Visual" and "Visual's context is withheld until Copy actually passes"; (3) every sub-recipe stays independently fetchable (`npx --recipe=marketing-director/copy-only`) so Remy's reusability rule is kept, not locked in; (4) the Studio graph (feature 4 above) is a live status board — pass / fail / pending per node — not a picture of "this calls that." Nobody surveyed verifies *between* chain stages. If this ships, that is the differentiator, not a feature-for-feature match. Sequencing: `runs:` metadata can ride with role recipes (funding-order step 3 / Stage 2); the inter-stage gate reuses `src/check/` and belongs with the eval panel, not a new engine; do not pull it ahead of catalog content.

  **Skill Atlas declined 2026-08-19 — screenshots of Remy's Obsidian-style graph, not a reason to build one.** Library view: 78 skills, 3 packs, departments (Brand / Content / Newsletter / Marketing / General / Personal), third-party packs (Sophron, Corey Haines, Matt Pocock), list recency (`never`, `1x · 5h ago`), `SKILL.md` body with git path in the footer. Graph view: 117 connections, color blobs, two edge types — **orchestrates** (arrow) and **related** (undirected). Header itself splits the useful number from the party trick: Library says "6 connections in focus"; Graph says 117. Ask overlay: job-shaped placeholder ("I'm trying to… which skills?"), two query types already in bounds — "what next in this chain" (newsletter research → intake, with a human-availability fork) and "which skills for this job" (decision-making → `llm-council` / `grill-me` / `grill-with-docs`).

  **The atlas is a good screenshot and a weak working tool.** Seeing everything at once is the problem it pretends to solve. At 78–180 nodes the canvas is a hairball: you can tell *that* things are related, not which chain to run, what already passed, or what is dead. **Related** edges are the hairball generator — similarity at atlas scale. If Tastefield ever draws edges, draw only `runs:` / orchestrates, never a related web over the catalog. An atlas of every skill is the Site IA's declined top-level Skills directory, just spatial — same spirit as non-negotiable #7: dumping the whole corpus is the failure mode even when the dump is pretty. Departments as filters map onto existing domain tags; do not add a Remy-shaped department axis. Faded third-party packs are a decent *metaphor* for installed-but-not-rolled-in (guest recipes / marketplace packs vs first-party) and a fine marketing still, not a spatial pack browser to ship.

  **What to keep from the screens, none of it the force-directed map.** (1) **Library, not Graph, is the working surface** — department filter → list with recency → `SKILL.md` body. Graph / Library / Usage as three views of the same data is the right IA; Usage as a first-class tab is stronger than bigger dots. (2) **Recency in the list is the cull signal** (`never`) — the usage-tally hook shown where people scan, not as node size. (3) **Ask is the discovery layer; the graph is wallpaper behind it.** The two screenshot queries are recipe-fit and chain-what's-next already specced; Tastefield's version of the "if Remy isn't available" fork is not a person-availability check, it is "did this stage pass `check_compliance`." (4) Feature 4's "recipe-dependency graph" means one recipe's `runs:` list as a live status board, never a catalog atlas. The moment a map needs a search bar *and* zoom controls to be usable, the list has already won.

  **Studio is not multiplayer today — a gap, not an omission in the write-up (2026-08-19).** No presence, co-editing, comments, or concurrent humans on one draft anywhere in this file. "Agent-write authoring, human keeps the taste calls" is one human approving one agent. Draft → Publish is a solo flow. Phase 3's agency workspace is the closest named multi-tenant surface, and it is unstarted and already sequenced *behind* catalog + Studio + Copy. Do not close this gap by building Type: a hosted canvas with Slack as the side door.

  **Five harness-native multiplayer shapes, none of them a live canvas.** Shared state is the compiled recipe repo the harnesses already read. (1) **Git-native async review.** The public submission-review gate already specced for the registry — propose, visible, feedback on specific parts, approval changes state — is borrowed from the pull-request mechanic. Currently scoped only to *public* listings; extending it to private team drafts is a scoping sentence, not new engineering. Reviewed in the org's GitHub the way engineers already review code. (2) **Chat-driven editing from each person's own session.** Agent-write authoring is not one person in one Studio tab. Any teammate, from their own Claude Code / Cursor / Codex session, proposes an edit to the shared compiled draft; it lands in one place. Many sessions, one repo — not many cursors on one screen. (3) **Corrections-become-restraints is already multiplayer, never named that.** Any teammate's session generating a correction produces a candidate restraint for the whole team, asynchronously. Naming/positioning, not a build. (4) **The usage-tally hook (logged this same day) as light shared visibility** — who's using what, without shared cursors. (5) **Ambient stays the side channel, inverse of Type.** Type's core is the hosted workspace; Slack is the door in. Tastefield's core stays the harness; Slack/Grok Bot, if built, is notification and light triage into a repo the harness already writes — never where real editing happens.

  Citable line if this ever sits on the marketing site: **Type built a shared workspace with a side door into the tools people use. Tastefield's shared state is a repo those same tools already read and write — there is no side door because there was never a separate front door.**

Status: vision, not roadmap. No phase number, no committed work. Don't let this bleed into Phase 2/3 descriptions until it's actually decided.

## Open questions — not decided, don't build against these

- **Should Tastefield recipes be discoverable through @skills' open protocol, not just the registry and MCP server (2026-08-15)?** The extensible source-connection list and the agent-readable setup file idea were both decided on the same logic — ship broadly, don't pick one channel. @skills (atskills.one, see Competitive landscape) already has a "design visual" category with 60,000+ skills referenced through it — being present there is a reach question, not a governance question, since the compiled, checkable rule underneath a recipe stays exactly what it is regardless of which channel surfaces it. Not decided: whether packaging recipes for a second, general-purpose discovery layer is worth the effort before the registry itself has any real content in it.

  **Third generic directory, 2026-08-19: agentskills.me is not a reason to decide this yes.** Same reach-not-governance logic, worse economics: 492 editorially curated listings, nicer UX than skills.sh, live sponsorship, and a gated creator-marketplace already on that turf. Listing compiled recipes there (or building a Tastefield-branded Skills index to match) would put the *exposed* half of the product (generic category starters) onto a lane that is getting more crowded, not the defensible half. Default stays: wait until the own registry has real category/role content; if a channel is added, prefer @skills' protocol (agents can `@`-mention without a human browsing a directory) over another human-browse SKILL.md gallery.
- **Same question, second channel: should recipes be shadcn-CLI-installable (2026-08-15, from beUI, firmed up 2026-08-15 by agentcn)?** shadcn's CLI has become an open registry protocol beyond shadcn's own components — beUI (see Studio, fifth source path) distributes entirely through it. A concrete technical shape already exists to copy rather than invent: beUI exposes plain, agent-readable endpoints per component (`/r/{slug}.json`, `/r/{slug}/raw`, an `llms.txt` index) so coding agents can read without scraping the UI — the same pattern a `@tastefield/fintech-trust-first` recipe could follow, `npx shadcn add`-able like any other registry item. No longer speculative: agentcn (see Competitive landscape) is shadcn-labs' own extension of this exact registry format beyond components into full composed patterns, `npx shadcn add @agentcn/eve/deep-search` — the same ecosystem beUI publishes into, actively building toward exactly this shape. Same reach-not-governance logic as the @skills question above; not decided whether to build either, both, or wait until the registry has real content to distribute.
- **Hosted Recipe API (`mcp.tastefield.com`)?** Raised in 2026-08-13 strategy sessions: a live endpoint that lets a third-party app (e.g. one built with Pixel Point's Toolcraft) fetch brand rules at runtime and merge them into end-user prompts before hitting an LLM. This is content governance for end users, not code governance for developers — a different product surface than anything built today. It also cuts directly against non-negotiable #1 (no telemetry, nothing sent anywhere, local-only) — not because it's telemetry, but because a queryable network endpoint is a different trust model than "runs on your machine, phones home to nobody." Don't build this without explicitly revisiting whether "local-only" is a permanent constraint or a Phase-1-only one. If it proceeds, it should be its own roadmap phase, not a sub-bullet under a GTM idea. Context.dev's credit-metered pricing (see Competitive landscape below) is a concrete reference point if this moves forward, rather than inventing pricing from scratch. Implementation option, 2026-08-14: Monid (monid.ai) already brokers per-call payment and agent-discovery for 1,300+ third-party tools — listing Tastefield as a provider there is a third path alongside "build it" and "don't," avoiding bespoke payment/metering infrastructure. Early-stage (v0.1.0) — worth knowing, not worth betting real integration work on yet. Access shape, 2026-08-15, from Vessa: split read from write cleanly if this ever proceeds — unauthenticated, no-login read (a public JSON an agent fetches directly) versus authenticated write requiring human oversight. Read is the low-risk half; write is where the non-negotiable #1 tension actually concentrates.

  **Real-world confirmation of the underlying tension, 2026-08-18 (see Carl Sziebert's ux-agent-skills, Competitive landscape).** A skill that executes entirely inside the buyer's own agent has no server in the loop for x402 to meter — the identical local-only-vs-hosted-endpoint fork this bullet already describes, just showing up in a different, adjacent product instead of staying hypothetical. If Tastefield's own recipes ever ship for local, in-agent execution *and* a hosted, agent-callable verification/fetch API, keep the two surfaces deliberately separate (free/open local path, metered hosted path) rather than assuming the free path funds the paid one automatically.
- **Does `src/scan/` extract from a live URL, or only a repo?** Both the Specimen Wall hero (paste `stripe.com`, watch tokens extract) and the registry's real-company recipe variants (see below) assume Tastefield can point at an arbitrary live site and pull its tokens. That's a different pipeline than parsing CSS/cva out of a repo someone gave access to — DOM/rendered-CSS scraping vs. source parsing. Confirm this exists, or scope it, before committing further to either. Buy option, 2026-08-14: Context.dev's `/web/extract` (arbitrary JSON-schema extraction from any URL, JS rendering and anti-bot handling included, $25/mo Developer tier) could power this without building scraping infrastructure from scratch. Real tension worth deciding on purpose, not backing into: this would make a hero demo and a sourcing lane depend on a company also listed as a competitor below — ongoing cost and vendor dependency, not a one-time build decision. Build option, also 2026-08-14: tastelab.xyz — a free, single-developer Claude Code/Gemini CLI skill — does exactly this with Playwright MCP (scrape a live rendered site, extract tokens + reasoning). Real evidence the capability is buildable by one person, not just purchasable from a funded vendor.

- **The market's load-bearing assumption: governance stays separable from generation (2026-08-15) — the one risk without an execution fix.** Every player in this landscape, Tastefield included, assumes you can bolt judgment onto someone else's generation engine rather than needing to own generation yourself. That assumption is already under pressure from both directions at once: Adobe's brand brain already learns continuously from every reviewer decision, not just an initial upload; Taste Labs already sells "give frontier labs taste" directly to the labs, not just to app-layer companies. If a frontier model starts absorbing company-specific taste natively — ingesting a connected repo at session start, the way `check_compliance` reads one now — the standalone compiled layer gets squeezed from both ends: the model gets better at this on its own, and generation platforms (Higgsfield, Hyperagent) build the same capability directly into their own product. Unlike the other open questions above, better sequencing or scoping doesn't fix this one — it's a real bet on the market's shape, not an execution risk.

  **A concrete instance, closer than a frontier lab, 2026-08-15: zeroheight.** Not hypothetical absorption by a model — a real, massive, enterprise-embedded incumbent (20% of Fortune 100, Uber and Decathlon named customers) already moving hard into "agents build from your design system" positioning, with a live MCP server and Claude/Cursor already in their own integrations bar. The honest version of the moat question, stated plainly rather than assumed away: `scan`/`compile`/`check`/MCP is exactly the kind of thing AI makes cheap to rebuild, and zeroheight already has the distribution, enterprise trust, and AI-agent positioning a from-scratch competitor would need years to earn. What still holds, and it's the same distinction as the Medium design-lead source: zeroheight's core mechanism is human-authored, human-maintained documentation served to agents, not automatic extraction from live shipped code — a real, structural difference, not just a head start. What doesn't fully hold: the belief that the engine alone is safe just because it's technically differentiated today. Durability has to come from what accumulates on top of the engine — a real customer's compiled history with real corrections, real Stage-0 relationships, public Arena reputation, Machinekind actually proven — not from the engine remaining hard to copy indefinitely, because it won't.

  **A second concrete instance, even closer to the literal mechanism, 2026-08-19: Figma Dev Mode MCP.** Different in kind from zeroheight — not a documentation-and-serve incumbent, but Figma's own MCP server, which can now "scan your codebase and output a structured rules file." That is the single most notable large-incumbent move toward the *extraction* half of Tastefield's mechanism specifically (real shipped code, not human-authored docs or a marketing site), and it comes from the most distribution-heavy incumbent in this entire landscape. It still lacks the other half — no deterministic compliance/lint gate served back over MCP was found alongside the scan-to-rules-file feature, the same enforcement gap already drawn against every advisory tool in Competitive landscape, just now confirmed inside the one incumbent best positioned to close it fastest. This is the concrete, named trigger for revisiting strategy, not a vague "watch the incumbents": Figma (or Cursor/Anthropic) shipping that gate on top of the scan it already has, not the scan alone.

  **A third concrete instance, 2026-08-19: Supernova's prototyping sunset.** Different shape from both zeroheight (docs-to-agents) and Figma (scan-to-rules-file): an enterprise design-system *platform* that already had tokens, components, docs, and a hosted MCP, then explicitly killed its generator (Create) to become "the context your existing agents already use." Validates the load-bearing assumption above from the other direction — they also bet that governance/context stays separable from generation, and they abandoned owning generation. The squeeze risk is not that they generate; it's that "scoped MCP context + component APIs + feedback + codebase usage snapshots" becomes the default enterprise install, and Tastefield is asked why a second MCP exists. Answer stays `check_compliance` plus local-no-account plus public recipes, or there isn't one. Full write-up in Competitive landscape; four named triggers there.

  **Companion evidence, both directions, 2026-08-15.** A real, live "AI memory portability" ecosystem already exists — Mem0, MemoryLake, and notably Supermemory, an MCP-based memory graph connecting ChatGPT/Claude/Cursor in one setup — the exact same delivery mechanism Tastefield already bet on, independently arriving at the same architecture for a different kind of context. One piece of enterprise research on this space (Atlan) states Tastefield's own reason to exist almost verbatim: "MCP standardizes how agents connect to data and tools. It does not, by itself, certify that the definition being delivered is current or approved." External validation that the pipe (MCP) and the guarantee (compile + check + curation) are genuinely separate problems, not the same one. But it cuts both ways on the absorption question above, worth holding as a real, unresolved tension rather than picking a side: if the market converges on open, vendor-neutral portable-context standards, that's hospitable ground for a standalone compiled layer to keep mattering. If it converges on frontier models and generation platforms absorbing this natively instead, that's the squeeze described above. Both are live possibilities right now.

  Difficulty, broken down: isolation itself is the easy part — integrate an existing sandboxed runtime (StackBlitz WebContainers, CodeSandbox Sandpack) rather than building container infrastructure from scratch. Dependency resolution is the actual hard part — an arbitrary customer's real repo (node_modules, peer deps, monorepo path aliases, custom PostCSS/Tailwind config) is a much harder build target than a clean demo repo, and this is typically where effort actually goes, not the sandboxing itself. Sample-prop inference for a meaningful render is a real but smaller third problem. Ongoing cost, not one-time: both WebContainers and Sandpack's own operators have had real sandbox-escape issues historically — this is a standing security commitment, not a box to check once. WebContainers also carries a commercial license at real usage volume, not free to embed at scale.

  Staged path, avoids committing to the hardest version first: if a customer already has Storybook, embed their existing static Storybook build — zero arbitrary execution, sidesteps the problem entirely for that subset. Reserve WebContainers/Sandpack for customers with no Storybook at all, which is the actual case this question is about — lets the harder investment wait until it's clear how many customers need it.

### Taste Arena — mechanics detail

**Task viability, learned from Taskmarket's own live data (2026-08-14).** Their open tasks sit at mostly zero bids despite 19.5K registered agents — visible evidence of what makes a listing dead on arrival. Three criteria a listing needs to clear: (1) a real, checkable win condition ("build the `neobank` variant of `fintech-trust-first`, passing these five `check_compliance` rules" — not "make a living world in six seconds"), (2) reward proportionate to effort (their 0.008 USDC tasks are a rounding error with a headline, not an incentive), (3) reaching a narrow, relevant audience rather than a firehose a specialist has no reason to scan. Fill-a-variant-gap, improve-a-weak-recipe, and propose-a-6th-category all clear this bar today.

**Self-generating bounties from passive detection — the actual fix for Taskmarket's liquidity problem.** Three signals generate a listing with no human authoring it: taxonomy gaps (an empty category/variant cell), coverage gaps (`check_compliance` hitting a pattern with no matching rule, across real projects), and weak/stale recipes (`src/bench/` density worse than siblings, or a lane-1 source guide that's since changed — watchable via something like Context7's Monitors feature, which watches any URL for changes). Rewards pool rather than being funded per-listing: every time the same gap gets detected again, a small amount adds to a standing reward for that gap, growing on its own until someone fills it. Maps onto Taskmarket's own modes: Claim mode for taxonomy gaps (first qualified agent reserves it, guaranteed pay for qualified completion), Benchmark mode for weak/stale recipes (`check_compliance`/`src/bench/` auto-score the improvement, a human only breaks ties). Funding: a slice of the Phase 3 agency retainer could seed a base pool per category; if the hosted Recipe API question resolves yes, a sliver of each paid fetch could route back in. One real tension, not optional: the coverage-gap signal means something leaves a customer's local scan to inform a public pool — needs to be opt-in and genuinely anonymized (a category label, never code or project identity) or it shouldn't feed the pool at all, per non-negotiable #1.

**Role × JTBD is what makes the taxonomy-gap signal apply to role recipes at all (2026-08-20).** The first signal above assumes a grid with empty cells; product categories have one, roles were four bare names, so the mechanic silently only covered half the registry. Job-to-be-done variants (see Public registry) create nameable, demand-backed holes — and the ask box's failed lookups supply the demand evidence, so a role bounty arrives with a real query behind it rather than a curator's guess. Also improves the matchups themselves: blind pairwise voting is noisy between unrelated recipes and clean between a parent and its fork, where one variable moved. That is eval mechanic (d) (Studio, eval panel) with a controlled comparison instead of an arbitrary one.

**Stay bounded to the existing domain axes — don't widen the category.** Taskmarket's own task list (worldbuilding video, game restaging, crypto referrals, PR merges) is a cautionary example, not a template: a market with no natural source of its own demand takes whatever it can get. The self-generating-bounty mechanism above already solves the liquidity problem within a narrow niche, which is a better answer than going broad. Room to grow exists *within* the domain axes already defined in "Two axes, deliberately not merged" (visual, brand, copy, motion, architecture, content, conversion, process) — copy/voice tasks, accessibility-audit tasks, motion-spec tasks — all still squarely design/dev, none of it general-purpose gig work.

**"Beyond design" clarified, 2026-08-15: build what's already named, not a new scope.** The domain axis was never design-only — copy, content, conversion, and process are already listed and already legitimate. Almost every concrete example built out so far (fintech-trust-first, saas-dense-dashboard) leans visual/brand-heavy simply because that's what got built first, not because the taxonomy is narrower than it looks. Expanding "beyond design" means actually populating the copy/content/conversion side of the existing axes, not deciding to cover new ground.

**A second, usage-based leaderboard, distinct from the creator one (2026-08-14, from Context7's Rankings page).** Not creator reputation — real usage: which registry categories/variants actually get queried by real agents, and which coding tools (Claude Code vs. Codex vs. Cursor) pull from Tastefield most. Serves two jobs: a public trust signal ("real usage, not vanity metrics"), and a live prioritization signal for the self-generating bounty mechanism above — a category queried constantly with no filled variant is a stronger bounty candidate than one nobody's asked for yet. **Mechanism, 2026-08-19, from Remy's plugin hook (see Vision):** a hook fires on every recipe read and tallies use. Previously a good idea with no implementation shape; this is that shape. Same opt-in/anonymized discipline as the coverage-gap bounty signal — no exceptions for "it's just usage counts." Backlog item; does not pull the Arena forward.

**A public submission-review gate, distinct from ranking (2026-08-15).** Bradley-Terry voting answers "which of these is better" — ranking among things already in the pool. A different question needs its own mechanic: "should this specific submission be accepted at all." Borrowed pattern, generalized from the pull-request mechanic — propose, becomes visible, feedback attaches directly to specific parts, async inspection, approval changes an explicit state, the whole thread persists afterward. The public counterpart to Studio's private compiled-draft review, not a duplicate of it. Built triage-first by design, not as an afterthought: `check_compliance` screens every submission before a human ever sees it, and only what's compliant-but-judgment-worthy reaches a review queue. Reason this matters from day one, not later: this exact mechanic is currently buckling under AI-generated volume in its own home domain — LinearB's 2026 benchmark (8.1M PRs) found only 32.7% of AI-assisted PRs merge within 30 days against 84.5% of manual ones, reviewer pickup time up roughly 5x, and a separate study found 61.38% of agent-authored PRs receive no recorded review at all. The reason given: "review was designed around writing being expensive... that assumption is what's gone." The Arena already anticipates agent-submitted volume (see creators, above) — adopting this mechanic without automated triage first would hit the identical bottleneck, not a hypothetical one. Second triage layer, 2026-08-15, from The Vibe Marketing Playbook's "Expert Review Framework": spin up 3-5 specialized reviewer personas (a brand-voice specialist, an accessibility specialist, a category-specific expert), each reviewing independently, synthesize where they agree — a real, reusable pattern for stretching human review capacity without just adding more humans. Sits between `check_compliance`'s deterministic pass and the human queue, not a replacement for either.

**Why anyone actually submits, 2026-08-15 — has to outweigh a real cost, not just list upside.** Money: recipe sales (Aura-style, $29-39/template), bounty payouts for filling a detected gap, usage-leaderboard visibility creating demand for whoever fills a category first. Reputation as a checkable portfolio, not a claimed one: the dual leaderboards function the way open-source contributions function for engineers. A pipeline to real paid work outside the platform entirely — Taste Labs' actual TasteMakers program already runs on this exact mechanism, "paid projects... no middleman markup." A separate, different-shaped incentive if it's a company publishing its own compiled system rather than an individual creator: closer to why companies publish open design systems today (Polaris, Carbon) — credibility and recruiting, not marketplace income. All of this has to outweigh the real cost of exposing work, which is exactly what the paid/free mechanism below exists to offset.

**Differentiated from Design Arena, 2026-08-14 — same proven mechanic, different axis.** Design Arena runs blind pairwise voting, Bradley-Terry rated, at real scale (5.1M+ users) — but it ranks *foundation models* against each other, not recipes or creators. Funding and scale update, 2026-08-19: operated by Intelligence, co-founded by Grace Li and Kamryn Ohly, raised a $7.9M seed led by Index Ventures (with Conviction, A*, and Valkyrie/Y Combinator), announced Aug 3, 2026 (TechCrunch); per Li, the team scaled "from $5M to $60M ARR and 5.5M users across 190+ countries" in six months as a team of ten. Real, funded, and growing fast — still operating at the model-ranking/eval layer, not the deterministic-governance-of-a-codebase layer, so the differentiation below holds unchanged. Reuse the mechanic exactly, change what's being compared: two Tastefield recipe variants applied to the same generation task, blind, voted head-to-head — "which governance produced the better on-brand result," not "which model is best." Two things neither Design Arena nor Taste Labs (see Competitive landscape) can do, because neither has an enforcement engine underneath: (1) a dual-axis leaderboard — Taste (the crowd vote) alongside Compliance (an objective `check_compliance`/`src/bench` score against the category's actual rules), not vote-only; (2) votes settle real money, not just a benchmark score — a match-up is literally two candidates for a specific taxonomy gap, and the winner collects whatever's pooled in the self-generating bounty above, wiring the vote directly to the marketplace instead of leaving it as a side metric.

**Compliance compounds with proven use, not a one-time gate score (2026-08-15) — reputation as a byproduct of normal use, not extra work to contribute.** This is the same mechanic already running elsewhere in this file, just not previously named as one: "when a creative director rejects output and says why, that correction becomes a candidate restraint" is reputation-as-byproduct applied to rule quality — nobody does extra work, the correction was happening anyway. Applied here: a recipe's Compliance score shouldn't stay a one-time gate check from submission. A recipe used cleanly across real deployments with zero corrections needed is a more trustworthy artifact than one that merely cleared the bar once — the marketplace principle that every clean transaction should make the next adopter's decision easier. Respects non-negotiable #1 by reusing an existing pattern rather than inventing a new tension: opt-in and anonymized, the identical shape already governing the bounty system's coverage-gap signal. A clean pass reports anonymously if opted in; no opt-in, no signal, no penalty either way.

### Editor-first hero — the Skill Studio as the landing page (proposed 2026-08-19)

**The change: the hero stops being a demo of the engine and becomes the product's first screen.** Previously the wall was something to watch; this makes it something the visitor is already inside. The Specimen Wall is not replaced — it gets demoted from "the hero" to "the evidence panel of a run," which is a stronger job for it, because a before/after that a stranger *caused* argues better than one that loops on its own. Keep the auto-pulse loop as the idle state before the first run, exactly as already specced.

**Input mechanic, decided 2026-08-19: paste a source (Option B), inside the hybrid shape below.** Five options were weighed — a skilltune-style prompt box, paste-a-source, a pre-run specimen editor, a hybrid of the last two, and paste-the-*output* ("paste your component, see what fired"). The prompt box is explicitly not the direction: it is identical to skilltune on the one surface where differentiation matters most, and it demos generation-from-description, the lane already declined. Paste-a-source wins on a structural argument rather than taste — the whole thesis is compile what already exists, so a source input says the positioning before any copy does, and it is the entry point the creative audience actually requires (see the audience question in Open questions). Day-one accepted sources, ordered by existing engineering readiness: a GitHub repo URL (already covered by the decided source connection), a pasted `SKILL.md`, pasted code or a component, an article or post. Live-site URLs and video/podcast links wait — the former is blocked on the still-open live-URL scan question, the latter on the transcript pipeline and consent guardrails in Vision. Paste-the-output remains the strongest candidate for the hero's second act, since it is the only mechanic here structurally unavailable to skilltune or agentskills.me.

**Page order, one idea per screen, no section that exists only to have a section.**

1. **The run.** A single input and a working editor above the fold, pre-filled with a real skill so nothing starts empty (the Little Plains warning already recorded: a blank chat-first input "asks visitors to know what they want before they've seen anything"). Two entry paths, both landing in the same editor: start from a first-party recipe, or paste a source (a repo, a URL, or a link per the BibiGPT-pattern note in Vision).
2. **The verdict.** Press Run. Governed and ungoverned arms generate against a locked task set; the Specimen Wall renders both with violation callouts pinned to the specific rule that fired — a hardcoded hex, a hallucinated prop, a missing confirmation dialog. The number reported is measured violation density, never a compliance percentage (non-negotiable #3).
3. **The edit.** Change one restraint, run again, watch the number move. This is the whole pitch in one gesture and it needs no copy explaining it. Everything to this point is anonymous — no account, nothing stored, nothing sent.
4. **The gate, placed where it's earned.** Save, fork, version history, and Publish require login. Correct instinct and worth stating as the rule: the account buys *persistence and distribution*, never the ability to see whether the thing works. A signup wall in front of the verdict would sell the one thing the page has to give away.
5. **The export row.** The harness logos as a functional element, not a trust badge — pick a target, get the artifact. See distribution channels below.
6. **Honesty tiers instead of a roadmap section**, per the pattern already taken from Blume: shipped features unbadged, `Soon` inline, a separate "on the horizon" block. The registry, the Arena, and every unbuilt domain go there, labelled by distance.

**Tone, since the ask was specifically that this be tasteful.** skilltune's page is the right *structure* and the wrong *volume* — it makes an unfalsifiable headline claim ("+20%"), then spends nine sections defending it. Invert that: one interactive artifact makes the argument, the copy stays declarative and small, and every number on the page is one that survives a live demo. The differentiating sentence is short enough to be the headline — **"Everyone else grades the skill. We grade what your agent shipped."** — and it is defensible only as long as the eval stays deterministic (see skilltune, Competitive landscape).

**Blocking prerequisite, not a detail to discover during build.** The hero's central number depends on the benchmark this file already lists under What is NOT done: run once, synthetically, both arms hand-authored by the same agent. Publishing a headline figure from that run would violate non-negotiable #3 and would not survive anyone re-running it. Order of operations: land the real two-arm benchmark (two actual agent sessions, task set locked immutable first, per skilltune's own eval discipline) *before* any number goes on the page. Until it exists, the hero can still ship — it shows the callouts and the density delta for the visitor's own run, which is a live measurement rather than a marketing claim.

**Distribution — export is the floor, not the answer.** Asked directly, "any other ways besides exporting": six, four already decided or specced elsewhere in this file, plus a seventh added the same day from Remy (see Vision). (1) Per-harness file export (Claude Code, Cursor, Codex, opencode, Gemini CLI) — table stakes, matched to skilltune's one-click export. (2) `npx @tastefield/mcp --recipe=X` — the named, browsable install path already decided. (3) The opaque share link (`npx skills add https://tastefield.sh/p/<id>`) for unlisted drafts, already decided. (4) **The MCP server itself, which is the actual differentiator and should not be listed as one option among equals** — an exported file is a copy that goes stale the moment the recipe changes; a live MCP connection is inside the agent's own tool-use loop, and it is the only channel where `check_compliance` can run *after* generation rather than just feeding rules in beforehand. Everything else distributes advice; this one distributes enforcement. (5) The shadcn-CLI registry format and (6) the @skills protocol — both still open questions above, both reach-not-governance, neither decided. Publish `agent-setup.md` / `/.well-known/agent-skills/site-skill.md` alongside whichever ship, per Backlog. (7) **A Tastefield plugin marketplace repo, 2026-08-19** — same compiled recipes, installable via Claude Code `/plugin` and the Codex equivalent, with org-wide auto-update on Claude Enterprise so a marketer never opens a terminal. Reach-not-governance, same logic as (5) and (6), cheaper than either because it is packaging of content that already has to exist for (2). Does not replace MCP; an exported/plugin-copied skill still goes stale the way (1) does. The live MCP connection remains the only enforcement channel.

### Marketing-craft transfers from Klint (2026-08-20)

Seven lessons from the best-executed agent-native marketing site found in any sweep so far (tryklint.ai — see Competitive landscape; a social-context API, not a competitor, and useful *only* as a craft reference). Sorted honestly: three change what gets built on the page, four confirm decisions already recorded above and are logged so they don't get re-derived as though they were new. The four operational principles behind lesson 5 live under Architecture, "Determinism discipline," rather than being restated here.

**New — changes the page.**

1. **Make the run tabbed across surfaces, not one output panel.** Klint's hero shows the same job through Search accounts / Search posts / Extract tabs, then repeats the trick with SDK / API / CLI / MCP request-response pairs across four use-cases. Consistent with "one idea per screen" — this is one screen with several faces of one result, not new sections. Two guardrails, both already standing: tabs must not grow into the Parametric Tweaker (deferred) or a browsable skills catalog (declined twice).
2. **Add a one-line contrast FAQ, and hold it to one line.** Klint's FAQ opens with "How is this different from a scraper?" and answers in two sentences: a scraper hands you a caption and a video file and leaves the watching to you; Klint has already watched. The whole positioning, in one comparison. Tastefield needs the same block titled "How is this different from a skill pack or a taste profile?" — answered once: advisory tools inject accumulated taste into the prompt and never look at what came out; Tastefield checks the output against rules compiled from your real tokens. The substance is already established eight separate times in Competitive landscape and already compressed into the headline ("Everyone else grades the skill. The one-line discipline is the point — skilltune's failure mode is making a claim and then spending nine sections defending it.
3. **Promote agent-installable onboarding from a backlog file to a hero CTA, and address agents out loud.** Klint's most distinctive mechanic: paste one line — "Fetch https://tryklint.ai/docs/for-agents/coding-agents.md and set up Klint for this project" — into your coding agent, which reads the docs and wires itself in. Backlog already has `tastefield.com/agent-setup.md` and `/.well-known/agent-skills/site-skill.md` as files to publish; this promotes them into a copyable hero CTA with a visible two-audience split, plus the machine-readable docs conventions that make it work (append `.md` to any page for raw markdown, `/llms.txt` as an index, and errors that name the fix rather than just the failure). 4. **Render a believable structured result immediately, with a violation in it.** Already decided: the Specimen Wall's before state carries violation callouts (a hardcoded hex, a hallucinated prop, a missing confirmation dialog), and the verdict step pins each callout to the specific rule that fired. Klint's version adds one refinement worth taking — its credibility comes from showing the *record*, not just the rendering: labels, timecodes, performance-vs-baseline, all inspectable. Right register for a developer tool and already the direction here — with the local-only, no-account, `npx` story being a stronger version of the same promise than Klint can make, since Klint's "Start Free" routes to a Tally waitlist. ### Eval panel — design decided 2026-08-19, extending (not reversing) the skilltune note in Competitive landscape

The earlier restriction stands as written — no LLM-judged prose score as the *headline* metric — but it was too thin as guidance, because the eval is one of the most valuable things the Studio can ship. Three separate ideas were being collapsed into one: how a number is computed, what job the number does in the UI, and which claim it licenses in public.

**What is genuinely strong in skilltune's mechanic and should be copied outright.** A score turns unmeasurable prose authoring into a loop with feedback — draft, measure, improve, visible progress, ship — and that loop is why people will use the product at all, independent of whether the number is philosophically sound. Their baseline framing is also correct and almost nobody does it: comparing against *no skill at all* ("no skill · 51" → "ships · 93") asks the right question. Locking eval cases immutable before tuning was already flagged here as worth taking. And running the whole loop on the user's own Claude/ChatGPT subscription with no API keys solves cost and privacy in one move, fitting non-negotiable #1 better than a hosted runner would.

**What is actually weak, stated precisely rather than as a general suspicion.** Their eval cases are generated from the author's own description, then used to score the artifact that description produced — so the number measures coherence with stated intent, not correctness against anything real; a wrong description yields a confident 92. Tuning v1→v8 against that judge is optimisation against the judge, with the usual consequence that the score and the real-world behaviour can diverge. And the units are the judge's own scale, so a 92 on one skill is not comparable to a 92 on another, which is what makes "up to 20% uplift" unfalsifiable in the same way non-negotiable #3 already forbids for compliance claims.

**The design: three tiers, each labelled by what kind of evidence it is, never averaged into one number.** (1) **Deterministic floor** — run the recipe against a locked task set, run `check_compliance` on the output, report violation density. Objective, reproducible, comparable across recipes. Copy: banned phrases, missing disclosures, forbidden claims, reading level out of range. Architecture: a missing required child, an action in the wrong container, validation firing after navigation. Visual: off-palette hex, invalid cva variant. This is `src/bench/` today. (2) **Differential** — the same task set with and without the recipe, reporting the delta rather than an absolute. This is skilltune's baseline framing with a physical metric underneath it, and it is the only shape that satisfies non-negotiable #3, because measured reduction is a claim that survives someone re-running it. (3) **Judged ceiling** — for what genuinely isn't checkable (does this caption sound like us, does this composition feel on-brand), an LLM judge, a human, or the Arena's blind vote is the only available instrument. It ships, it just never appears unlabelled, never merges into tier 1's number, and never becomes the headline. **User-facing label, locked 2026-08-20, judged skills only:** "This skill is an LLM agent running with pre-configured instructions and context to steer the result. The output still depends on the prompting and context you give. It does not check." Do not put it on a recipe that runs `check_compliance`. A mixed recipe carries this callout beside a `Checked` label, never a sentence that averages the two.

**This is already the Arena's dual leaderboard, one surface earlier.** Compliance (objective) alongside Taste (crowd vote) was decided for the Arena on exactly this reasoning; tiers 1 and 3 are those same two axes rendered in the authoring panel instead of the public ranking. One mechanic, two surfaces — not a new metric to invent.

**A fourth axis nobody in this landscape is running: harness portability.** skilltune's step 02 picks one harness and one model. Tastefield's version runs the same recipe across Claude Code, Cursor, and Codex and reports violation density *per harness* — empirical, deterministic, no judge involved, and it answers the question an adopter actually has ("will this hold in the harness I use"). The consequence worth acting on: this is the same build as the benchmark listed under What is NOT done ("the MCP server has never been verified against a real IDE"). The eval panel is the instrument that closes that gap, run continuously against real recipes instead of once against a fixture. Treat the honesty debt and the product feature as one item, not two.

**Four eval mechanics worth building beyond a score, ranked by how much they differentiate.** (a) **Adversarial task sets** — generate tasks designed to tempt a violation (a checkout button for a brand that forbids red CTAs, a promo for a brand that bans "guaranteed"), since surviving temptation is stronger evidence than passing neutral work, and it makes a far better demo. (b) **Model-upgrade regression** — re-run a locked task set when the underlying model changes and report what broke; model upgrades silently degrade skills and nothing in this landscape watches for it, which makes this recurring value rather than one-time authoring value, and it compounds because it requires accumulated locked task sets. (c) **Rule-level firing counts** — a restraint that never fires across 100 tasks is either perfectly obeyed or dead weight, and only a check can tell which; this is cheap, genuinely useful editorial feedback, and it feeds the coverage-gap bounty signal already designed. (d) **Blind A/B between two recipes** on the same task, borrowing the Arena mechanic early, confined to tier 3.

**What the rename must not drag in, since it reopens a question already closed twice.** The Site IA decision (Public registry, 2026-08-18, reconfirmed 2026-08-19 against agentskills.me) declined a browsable top-level *skills directory*, and that still holds — naming the authoring surface "Skill Studio" is not permission to build the catalog half that decision rejected. Authoring + verification is a surface nothing in the competitive set has; a skill gallery is a surface four products already have more of. Build the first, not the second.

External validation, 2026-08-15, from an unrelated context — current reporting on production Slack-AI integrations sets the same bar independently: "the agent can call external APIs and post a confirmation thread a human can approve or reject before commit — if an integration is missing that, it's a chatbot, not an AI integration." Same propose-then-approve shape, arrived at from a completely different direction, not internally reasoned in isolation.

  **Multiplayer reading, 2026-08-19, not a change of the mechanic:** this is not one person in one Studio tab. Any teammate, from their own harness session, proposes an edit to the shared compiled draft; approval still happens before publish. Many sessions, one repo. The public submission-review gate already designed for the registry is the same shape for private team drafts if that gate is ever extended inward — GitHub review, not a hosted co-edit canvas.

**What actually gets edited, and how (decided 2026-08-15).** Edits target Tastefield's own compiled draft — the state already implied by the mockup's DRAFT badge and Publish button, between scan and publish — never the original source. The repo, Figma file, or zeroheight guide stays exactly what non-negotiable's read-only source connections already promise: Tastefield's, never written back to. Structured token editing (color picker, numeric spacing field) is the default surface, not raw CSS — keeps editing inside "machine-checkable regex wherever expressible," the same discipline non-negotiable #6 already applies to scanning. A code view exists as an escape hatch for power users, not the default. `check_compliance` runs live during editing, not just at scan or publish time: change a token, see every referencing component update, get flagged immediately if the new value breaks an existing restraint — a coherence check nothing in the competitive set can do, because nothing else has the enforcement engine to run it with.

**Reviewing a system-wide change reuses the Specimen Wall, not a new visualization (2026-08-15).** When an edit touches the whole system — a full restyle, not one token — the review surface is the same before/after mechanic already fully specified for the marketing hero (auto-pulse, drag handle, click-to-pin), running live inside Studio instead of on the public page. One mechanic, two jobs: convince a stranger on the landing page, and let someone actually review a holistic change before approving publish. Keeps the demo and the real product experience the same thing rather than two things that happen to look similar.

**Two UX details worth matching, also from Packs:** form validation shows inline, on submit, next to the field — not a silently disabled button with no explanation. Destructive actions (deleting a recipe) get a visually separated "Danger Zone" that states the actual consequence in plain language ("its shared install link stops working"), not just a generic confirmation.

## Public registry — recipe taxonomy (Phase 1, not built)

Decided 2026-08-13. Recipes are browsed by product category, not by company name — a visual-only recipe like `linear-vibe` has no story; a real recipe (tokens + negative restraints + voice rules) does.

Naming: category-first, named for the problem solved — `fintech-trust-first`, `consumer-checkout-safe`, `saas-dense-dashboard`, `devtool-dark-first`, `healthcare-intake-careful`. Legible in ten seconds without recognizing a company.

Each category has variants, not one monolithic recipe. Example:

```
fintech-trust-first
├── institutional  — "boardroom conservative"  — navy/charcoal, dense tabular numerals, minimal motion
├── neobank        — "confident and modern"    — high-contrast mono type, one bold accent, generous whitespace
└── embedded       — "invisible and fast"      — near-zero chrome, built to disappear inside someone else's product
```

The mood caption ("boardroom conservative") is the picker — people choose a variant by vibe, not by reading a token table first. Presentation pattern borrowed from Refero's mood-caption style (see Competitive landscape) — not their data. Enrichment, 2026-08-15, from "Design Is How It Tastes" (see Studio, DESIGN.md critique above): the existing captions are object-language wearing a vibe label — "high-contrast mono type, one bold accent" describes the artifact, not the encounter. Pair each variant with a genuine sensory line alongside the existing description, not replacing it — the hush before a decision gets made, not the mono typeface — a natural extension of the picker's own stated purpose, not a new direction.

Confirmed 2026-08-15, against tasteprofile.io: a recipe page is meant to do double duty — human-browsable (mood caption, visual specimen) and agent-fetchable (DESIGN.md/tokens export) from the same one artifact, not two separate deliverables. tasteprofile.io's own hosted-viewer pitch is the identical shape, arrived at independently — good confirmation this is the right structure, not a course correction.

**A second, cross-cutting taxonomy dimension: role, not just product category (2026-08-15, from Hyperagent).** Everything above organizes recipes by what's being built (`fintech-trust-first`, `saas-dense-dashboard`). Hyperagent ships a named fleet of role-specific agents — creative director, social media manager, podcast producer — with no visible brand-governance layer behind any of them. A recipe scoped to *who's* building, not just what's being built, is a different, real thing: a `creative-director` recipe governing high-level brand-consistency judgment calls, a `social-media-manager` recipe governing caption voice and platform constraints, a `podcast-producer` recipe governing audio branding. Same compile-and-serve architecture, organized by role instead of output type — and it's what any of Hyperagent's own fleet agents would read from, making Hyperagent a plausible consumption point for the generalized brand-rules tool (see Vision), the same relationship already established with Higgsfield and Motion.

**Two separated sections in the registry, not one mixed list.** "Recipes by product category" (fintech-trust-first, saas-dense-dashboard, etc.) and "Recipes by role" (creative-director, social-media-manager, podcast-producer) answer different questions and get browsed for different reasons — mixing them recreates the exact "seems random" failure the category-first taxonomy was originally designed to fix.

**Role-section presentation, 2026-08-19, from agentskills.me/solutions.** Steal the IA, not the content: one landing page per role, a short list of concrete use-cases, each linking into the actual recipes — not a second flat dump of every skill tagged with that role. Their "Brand & Communications" page ("maintain consistent brand voice… apply company-specific document formatting… ensure consistent brand guidelines across outputs") is a live, generic, unenforced instance of exactly what `creative-director` / `marketing-director` already target. Confirms the Hyperagent-derived role cut; when the registry's "Recipes by role" section is built, use this page shape rather than inventing a new one.

**Role recipes get variants too, discriminated by job-to-be-done (2026-08-20). Not a fourth axis — the same variant slot product categories already have, with a different picker.** Product categories pick by *feel* ("boardroom conservative"); nobody hires a creative director by feel, they hire one for a job. So the role-side discriminator is a job statement, filling the slot `fintech-trust-first/neobank` already occupies. Four worked examples, same skill pool, different mixes — which is what a variant actually is, given a recipe is a bundle of skills plus restraints plus checkable rules: `creative-director/reject-an-ad` (copy + brand restraints, judgment list, no token grid — asset in, cited verdict out); `creative-director/brief-a-fleet` (brand + Visual case 2, ends by emitting the constraints other agents generate under); `creative-director/defend-a-call` (same restraints rendered as client-facing rationale with Evidence citations); `creative-director/audit-a-campaign` (a `runs:` chain over existing assets, batch drift detection). Install path is unchanged: `npx @tastefield/mcp --recipe=creative-director/reject-an-ad`. Role is the folder, variant is the SKU. Fixes a real asymmetry rather than adding structure — Stage 0 already assumed this by interviewing 5-10 directors *across* categories rather than averaging them into one generic `creative-director`.

  **Why this is the supply pump, and the specific gap it closes.** The marketplace's bottleneck is supply (already recorded), and authoring cost is what throttles supply. A JTBD variant is a remix — a different subset and ordering of skills already compiled — not a fresh compile, and the remix UI is already specced as Studio's Packs-sourced drag zone (GitHub import, drag & drop, search-the-registry-and-add with a running count). Aura's remix counts are the existing validation that people do this. Structural half, more important than the authoring cost: **role recipes currently have no empty cells.** The self-generating bounty mechanic detects taxonomy gaps as unfilled category/variant cells — product categories have that grid, roles are four bare names, so gap detection simply does not apply to the half of the registry this file calls the defensible half. Role × JTBD creates the first addressable holes there. See Taste Arena.

  **Detect the jobs, don't enumerate them.** A brainstormed list of forty JTBDs produces a mostly-empty grid, which is Taskmarket's zero-bid graveyard with better labels, and selling attention against an empty catalog is already ruled out. Three sources that already exist: Stage 0 interviews are a JTBD capture exercise, not background colour — "where they actually intervene or reject work and why" *is* the list; the coverage-gap signal (`check_compliance` hitting a pattern with no matching rule) is a job with no recipe; and the scoped ask box (Vision, Remy note) is a demand sensor — every "I'm trying to…" returning no good match is a named, demand-backed empty cell with evidence attached. Opt-in and anonymized, the job phrase only, never project identity — the same discipline already governing the coverage-gap signal under non-negotiable #1.

  **Three guardrails, all borrowed rather than invented.** (1) **Materiality test:** a variant must differ by something checkable — a different restraint set, a different `runs:` chain, or a measurably different violation density on the shared task set — never a renamed caption. Same "substantially reworked, not relabeled" condition already applied to the Refero sourcing lane; without it, trivial forks flood the catalog and reproduce the agentskills.me volume problem the registry is supposed to avoid. (2) **Domain filter still binds:** rejecting an off-brand ad is brand/copy/visual; a creative director running performance reviews is the sales-trainer exclusion wearing a different hat. (3) **"Mutation" stays a metaphor.** Selection can be automated (compliance scores, Arena votes); variation stays human-authored, or it is the auto-publish failure mode already declined against BibiGPT and forbidden by non-negotiable #4.

  **Pricing and bundling follow the existing lanes, no new mechanism.** A narrow, Stage-0-sourced JTBD variant is a natural Paid candidate at the Aura $29-39 point; a generic `creative-director` pack is a Free candidate competing against 60,000 free alternatives. The role landing page can sell individual jobs plus a full-role bundle that is just a `runs:` chain over them — reuses the pricing field and the chain metadata already decided, rather than inventing a bundle SKU.

**A third registry shape, flagged 2026-08-18, not yet a decided taxonomy addition: "guest" or borrowed-taste recipes.** Distinct from both category recipes (your own system, extracted) and role recipes (judgment for a role adjacent to your system) — a compiled archive belonging to a named individual creator (a brand critic, a copy specialist, a motion designer), sold or bountied as its own product, e.g. "run this ad through [critic]'s voice rules." Same domain × category tagging, same Trigger/Decision/Reason/Evidence/Trade-off restraint format, same Free/Paid gating already specced above — reuses the mechanism entirely (see the archive-to-agent-tool discussion in Vision). Kept a separate label rather than folded into either existing shape on purpose: category and role recipes both extract and enforce a real company's *own* decisions; a guest recipe imports someone else's taste on purpose — the same opposite-direction relationship already drawn against GetLayers in Vision. Mixing the label would blur that distinction the same way mixing product-category and role recipes into one list was already ruled out just above. Not decided whether this ships at all — flagged for whenever the registry has real category/role content first, per the same sequencing discipline already applied to the Arena and x402.

## Bugs already found and fixed — don't reintroduce

- **cva class strings contain colons.** `ghost: "hover:bg-muted"` — a naive parser reads `hover:` as a variant key. The parser is string-literal aware.
- **tsconfig is JSONC.** Comments and trailing commas mean `JSON.parse` fails. Alias reading uses a targeted regex.
- **Plurals.** `review-animations` didn't match `animation`. Term matching allows an optional trailing `s`.
- **Multi-word terms vs. hyphenated slugs.** `"design system"` never matched `design-system`. Haystacks are normalised (`-_/` → space) before matching.
- **Domain floor was above single-summary-match weight.** A skill described as "popup design and copy" reported neither domain. Floor is 6, summary match is 8.
- **Merging leaderboard views.** `trending` and `hot` report *windowed rates* in the same `installs` field as cumulative. Merging naively overwrites 770,700 with 4,100.
- **OIDC tokens rotate ~12h.** A stored `VERCEL_OIDC_TOKEN` secret dies before the next 3-day cron run. CI mints a fresh one from a long-lived `VERCEL_TOKEN`.

Klint is different in kind: it is rigorous, explicitly and in writing — fixed catalog rather than free text, evidence shipped beside every classification, `null` never a guess, 404-not-tracked rather than a partial record — but every bit of that rigor is about *honest retrieval of input*, not *checking output*. Nothing in it would catch a hardcoded hex against a real palette. Worth naming precisely because the vocabulary is so close to Tastefield's that a skim would mistake it for the same claim: determinism-of-retrieval and determinism-of-verification are different products, and only the second one is a governance engine. The four principles ported from it are under Architecture, "Determinism discipline"; the seven marketing lessons are under Landing page hero, "Marketing-craft transfers from Klint."

  **What makes the site worth studying at all.** A live, tabbed, product-as-hero query demo instead of a screenshot; a dual audience addressed out loud (humans *and* agents, with a paste-one-line agent-installable setup); a one-line category-contrast FAQ ("How is this different from a scraper? … Klint has already watched"); a determinism/trust block; a numbered 01–04 pipeline with stat counters; and zero-friction verb-led conversion copy. Same two-audience pattern Gamma's CEO described at SaaStr AI 2026 — build for the human while preparing for a world where many users are agents, without alienating either — so treat it as a 2026 table-stakes pattern Klint executes cleanly, not as a Klint invention.

  **Caveats, and they are large.** No founder, funding, launch post, pricing, named customer, case study, review, team size or HQ could be found anywhere as of 2026-08-20; the site is the sole source, "Start Free" and "Dashboard" both route to a Tally waitlist form, and the on-site creator handles are illustrative demo data. Its scale stats (500K accounts, 25M posts, 12K/day) are self-reported marketing claims with no third-party verification — relevant to lesson 6 above, where Tastefield's counters have to clear a much higher bar than Klint's do. Name collisions are severe enough to make ongoing monitoring noisy: a Copenhagen marketing agency, a Nordic VC, redk's Klint GPT Salesforce middleware, Le Klint lamps, a French Salesforce consultancy, and a nicotine pouch brand all share the name.

  **One trigger, and nothing observed suggests this trajectory:** re-evaluate only if Klint (or a clone of it) starts extracting a brand's own real design or content system and serving it as context, or ships a verification step on generated output. Absent either, it stays a reference, not a watch item — do not add it to the absorption list alongside `brandsystem-mcp`, Figma Dev Mode MCP, and Supernova.
- **Reference-library and asset-library brand tools — oh-my-design.kr and OnBrand by SlideSpeak (2026-08-19).** Two more found in the same sweep, worth naming precisely rather than lumping in with brandsystem-mcp above: oh-my-design.kr ships a DESIGN.md spec (see Studio) alongside 440 quality-graded company brand references for coding agents — a curated reference library, not codebase-extraction-plus-verification. OnBrand is an MCP brand-governance layer (logos/colors/fonts/layouts) for Claude Code/Codex/Cursor, but a brand-asset-library approach aimed at decks, not codebase extraction or a deterministic gate. Neither clears the bar brandsystem-mcp does; noted for completeness, not elevated to a watch item.

## What is NOT done

- **The benchmark has only been run once, synthetically.** 2026-08-13: 8 tasks, both arms hand-authored by the same coding agent (not two independent live agent sessions) against `test/fixtures/sample-app`. Baseline density 31.21 (49 errors / 5 warnings over 173 lines); governed density 0. Full output in `bench-runs/RESULTS.txt`. This proves the harness and checker work end-to-end on realistic code — it does **not** yet prove the claim against real prompt variance, since one author wrote both arms with full knowledge of what each arm was supposed to demonstrate. The still-open, higher-value version: collect governed/baseline generations from two actual agent sessions (e.g. Claude Code with vs. without the Tastefield MCP server wired in) and re-run `node dist/bench/run.js` unchanged against those. Discipline to borrow from skilltune.dev (see Competitive landscape), 2026-08-15: lock the task set immutable before running either arm, the same way their eval cases are locked before tuning starts — removes any possibility the task selection itself was shaped by knowing which arm needed to win.

  **A third, independent source converging on the identical discipline, 2026-08-19, from Little Plains' "Bypassing Figma & Building a Knowledge Product" essay.** Their own eval process for a completely different product (a studio knowledge/retrieval site, not design governance) is the same shape as skilltune's, arrived at separately: freeze a scenario set (74, in their case) covering the actual failure modes that matter — ambiguous inputs must trigger clarification rather than a guess, a request for "recent" must resolve to a real value rather than editorial ordering, a structured response must fit its output envelope — run each scenario multiple times (three, producing 222 outputs), then have a stronger model judge every output against the product's actual behavioral contract, not a vague rubric. Their own framing of the payoff, worth adopting verbatim as the goal for Tastefield's re-run: "the score mattered less than the failure list." Concrete, transferable scenario categories for Tastefield's own locked task set, not just the methodology: an ambiguous or missing token should force a specific, checkable fallback rather than an invented value; a check on a real off-palette hex must actually fire; a hallucinated prop or non-contract cva variant must actually get flagged — each one a real `check_compliance` behavior already claimed, not a new capability to build first.
- **The MCP server has never been verified against a real IDE.** The protocol handshake is smoke-tested with a real MCP client over stdio, which proves the plumbing — not that it changes what Cursor writes.
- Only the Phase 1 core engine is built. Phase 1's public registry, Phase 2 (Studio recipe workshop: token editor + Publish first; Tweaker deferred), and Phase 3 (agency workspace, CI/CD PR bot) are all unstarted. Strategy docs that describe the Tweaker in present tense are stale; it doesn't exist yet and is not the Phase 2 headline.
- Pricing ($99–299/mo agency, $10k–30k/yr enterprise) is unvalidated — no prospect conversations behind those numbers.
