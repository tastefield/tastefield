# Tastefield — working context

Read this before changing anything. It records decisions and the reasoning behind them, so they don't get quietly undone.

## What this is

Tastefield compiles a repository's existing design system into executable context and serves it to local AI coding agents over MCP. Positioning is **coexistence, not replacement**: zeroheight / Supernova / Storybook / Figma stay the human source of truth; Tastefield is the active layer that makes their rules stick inside Claude Code, Codex, and Cursor.

**Shipped trio updated 2026-08-17:** Windsurf swapped for Codex based on current usage, not a product change. Codex has not been tested end-to-end against the MCP server yet; it's listed as shipped on the assumption that a standard MCP server works with any MCP-compatible client. See `.agents/product-marketing.md`.

Phase 1 (core engine + public registry): the core engine is **built and passing 59 tests**; the public registry (browsable first-party recipes, `npx` install) is not started. Phase 2 (Studio — Parametric Tweaker, landing page) and Phase 3 (agency workspace, CI/CD PR bot) are also not started. Renumbered 2026-08-13 — see "Roadmap reframe proposal" below for why.

## Non-negotiables

These exist for reasons that cost real effort to learn. Don't "fix" them.

1. **No telemetry.** Nothing is sent anywhere. Git history is not read. The original plan included selling RLHF telemetry to frontier labs — dropped, because enterprise security teams blacklist MCP servers that phone home, and the indie users who'd allow it don't generate enough volume to matter.

2. **Unknown install counts are `null`, never `0`.** Rendered as an em dash. A fabricated install figure in a pitch deck is a credibility problem. There's a test enforcing this.

3. **Never claim "100% compliance on Pass 1."** Models are stochastic; the claim is unfalsifiable and won't survive a live demo. Report measured violation-density reduction instead.

4. **Curation is not automatic.** The scheduled sweep produces a *shortlist*. Category, status, rationale and recipe membership are assigned by hand. If that becomes automatic, this is just a worse mirror of skills.sh.

5. **Skills that fail a security audit never enter a recipe.** Test-enforced.

6. **The Tailwind v3 config is detected but never executed.** Running arbitrary code from a scanned repo is a security problem and configs import plugins that won't resolve.

7. **The MCP server has no `get_everything` tool.** Progressive disclosure only. Dumping a whole design system into a context window is the failure mode this product exists to fix.

## Architecture

```
scan(repo) → ScanResult → compile() → .tastefield/ → MCP server → agent
```

- `src/scan/` — CSS custom properties (incl. Tailwind v4 `@theme`), cva variant contracts, stack detection
- `src/compile/` — derives rules that cite the project's real tokens and components
- `src/check/` — one rule checker, shared by the MCP tool, the CLI, and the benchmark. One implementation so the claim and the measurement can't drift
- `src/mcp/` — four tools: `get_brand_standards`, `get_component_contract`, `get_design_tokens`, `check_compliance`
- `src/registry/` — skills.sh index: client, curation, discovery, momentum, snapshots, full sweep
- `src/bench/` — measures governed vs. ungoverned agent output

Rules carry a machine-checkable regex wherever expressible. A rule an agent merely reads is advisory; a rule that can be verified is enforcement.

**Restraint documentation format (2026-08-14), from tastelab.xyz.** Each negative restraint gets five fields, not a bare rule statement: Trigger (what decision prompted it), Decision (what was chosen), Reason (the logic), Evidence (specific proof — px/hex/DOM values, or the source guide citation for a real-company recipe), Trade-off (what it gives up). More rigorous than an unstructured restraint list, and directly reusable for the recipe taxonomy's Do/Don't sections.

## Two axes, deliberately not merged

- `domain` — what a skill is **about**: visual, brand, copy, motion, architecture, content, conversion, process
- `category` — what kind of **rule** it compiles into: structure, boundary, voice, motion, process

Skills are frequently multi-domain and must not be forced into one bucket.

Brand and copy matter more over time than visual rules. Base models keep getting better at spacing and colour on their own; they will never independently know that a company can't say "cheap" or can't use red on a checkout button for compliance reasons.

## Vision — beyond code (not built, not roadmapped as a phase)

Today Tastefield only governs code — the AI writing components inside an IDE. The longer bet: as AI starts generating more than code (marketing graphics, social assets, ad copy), something has to keep all of that on-brand too, not just the codebase. Working name: **Creative & Brand Intelligence** — extends Taste DNA (tokens, negative restraints, voice rules) to any AI generating any output for a company, not just a coding agent in Cursor.

Further out: a multi-agent setup where specialist AIs (a design agent, a dev agent, a review agent) transact with each other autonomously to complete a task end-to-end — an "agent economy" for design and dev work. Tastefield's role doesn't change in kind if that happens: it's still the layer making sure whatever comes out — regardless of which agent produced it, or how many agents the task passed through — matches the company's actual brand rather than generic AI output.

Sharpened further, 2026-08-14: this has a concrete buyer — one creative director directing a fleet of specialist agents instead of a team of people. More agents involved means more drift risk, not less, since nothing naturally keeps their outputs coordinated the way a human team stays aligned through meetings and shared context. The director is the person this vision was previously missing. Tastefield's role stays disciplined either way: govern whatever's dispatching the fleet, don't try to build the dispatching itself — same "coexistence, not replacement" posture already applied to zeroheight and Figma, applied here to whatever ends up doing agent orchestration.

Sharpened 2026-08-14, against Aura.build's creator marketplace: every marketplace model looked at so far (skills.sh Packs, Aura's template library, the Taste Arena idea below) is a human creator economy with AI in the middle — humans make things, humans browse and buy, AI just generates. The actual differentiation is a registry an agent can transact with directly: querying variants mid-task, paying for one via the x402 idea (see Roadmap reframe proposal), with no human browsing step in between. Creators don't have to be human-only either — an agent that authors a well-performing recipe variant could submit and rank on the same leaderboard as human-authored ones. The structural edge already available: Tastefield lives inside the agent's own tool-use loop via MCP; a marketplace a human has to browse and copy from isn't.

Made concrete 2026-08-14: Higgsfield already ships a live MCP server (mcp.higgsfield.ai) that works inside Claude Code and Cursor — the same environment Tastefield's own MCP server lives in. A single agent session could have both connected: Tastefield supplying brand rules (colors, motion pacing, logo placement, voice), Higgsfield generating the actual video, image, or ad. No generation infrastructure to build — Higgsfield already solved that at scale (25M+ users, 30-50+ aggregated models including Sora/Veo/Kling, direct enterprise sales to brands and agencies with IP indemnification). Tastefield's job stays exactly what it already is: compile and serve rules, not generate content. Real evidence this gap exists today, not hypothetically: Higgsfield's own published example prompt for building a website hand-types brand constraints into natural language ("celadon sage, warm ivory, pine ink, Cabinet Grotesk and Inter Tight, one red accent") because there's no structured alternative — the same "AI wasn't in the meeting where the rules got decided" problem this file opens with, just showing up as a human typing color names into a prompt instead of a hardcoded class.

The generalizable version, not a video-specific one: the actual product decision is one generalized brand-rules MCP tool — voice, restraints, motion, not just code tokens — that any MCP-compatible generator can read from, the same way Higgsfield says any MCP client can connect to them. Video, ads (Higgsfield's own Marketing Studio and UGC factory), and website-building (Higgsfield's own skill category, and Toolcraft from the very first strategy session) are three consumption points for that one tool, not three integrations to build separately. Resist chasing each generation category individually — the leverage is in the one generalized tool, not bespoke work per vendor.

Fourth consumption point, confirmed 2026-08-14: Motion (motion.so), an MCP/API-callable launch-video and motion-graphics agent, has a literal, named "Design system" slot in its own prompt UI, alongside Connectors, uploaded assets, and style references — a concrete, already-existing hook to point the generalized tool at, not a hypothetical one. Its "Research" step currently re-derives brand colors and type from a live site read on every run rather than a curated source — the same guess-from-scratch gap already found in Higgsfield's LOOMERE example, now confirmed twice independently rather than once.

Fifth consumption point, confirmed 2026-08-15: Hyperagent — a real, polished agent-orchestration platform shipping a named fleet (creative director, social media manager, podcast producer, editor) that researches, builds, and delivers real work. No visible brand-governance layer on any of it. Different in kind from the first four (a fleet-management platform, not a single generator), but the same underlying relationship: its agents are a plausible reader of the generalized brand-rules tool, same as Higgsfield and Motion. Also the clearest evidence yet that building an owned, competing agent fleet is a real, separate bet from building the rules engine — see the staged phasing below.

Sixth consumption point, confirmed 2026-08-15: GetLayers — a curated design-asset library (templates, 3D scenes, backgrounds) shipped as a real MCP server, with one capability closer to Tastefield's own scan-first pattern than anything found so far: "point it at your repo, it reads your code first, then proposes where a scene or motion belongs." A live tool reading an actual codebase before generating, not just a live site or uploaded context. Worth being precise about the difference, though, since it's not just another peer: GetLayers reads the repo for *placement* — does this look right sitting here — not for *brand fit*. Its whole value proposition is bringing its own curated aesthetic to a project; Tastefield's is extracting and enforcing a project's own. Nearly opposite directions on the same axis. Run ungoverned on a real brand, GetLayers' repo-aware feature has no mechanism stopping it from injecting a coherent-looking but completely off-brand aesthetic — a live illustration of exactly the risk `check_compliance` exists to catch, not just a hypothetical one.

Seventh consumption point, confirmed 2026-08-15, a genuinely different shape from the first six: ambient, workplace-embedded agents, not generation destinations. Grok Bot (xAI + Cursor, public beta since 2026-08-11 — six days old, launched following SpaceX's $60B acquisition of Anysphere, Cursor's own parent company, notable since Cursor is one of the three primary MCP clients already named in "What this is") already ships one-click plugin connections — Context7 shown as a live example in their own product — alongside custom plugin building, automatically choosing plugin (faster, reliable) over raw browser control depending on the task. A Tastefield connection is exactly the shape of thing that plugin panel already accommodates. Real use, not hypothetical: on-brand copy drafted directly in a Slack thread (Copy domain, marketing-director/social-media-manager role recipes, just triggered conversationally instead of through a build pipeline), or ambient checking — a design link dropped in a channel, `check_compliance` flags it passively rather than only at commit time. Worth naming as its own category: not a destination you go to generate something, but tasks handled wherever a team already talks. Gartner's cited projection — 40% of enterprise apps embedding task-specific agents by end of 2026 — is real signal this is a major, current category, not a niche one.

Second confirmation of this same category, 2026-08-15: Type (type.com) — a shared team workspace on top of existing Claude/Codex subscriptions, built by a team with real pedigree (Airbnb, Atlassian, Meta, Stripe, X), department-templated Spaces (Marketing, Product & Engineering, Support, Sales, Data, HR/Ops) pre-wired to real tools. "Best in class Slack integration — mention agents, route access by channel" is the identical shape as Grok Bot's, for Claude/Codex instead — two independently-built products converging on the same pattern within days of each other, stronger evidence than either alone. Their Marketing Space ("suggests content, improves ads, and monitors competitors") is real, described validation of the `marketing-director` role recipe, landing right after it was named. Not a governance competitor — nothing here touches design systems or brand compliance.

Pattern-level finding, now confirmed four times independently, worth stating plainly rather than as a single observation: Type's own pitch — "self-learning, shared memory... self-improving, reviews its own work and improves with time" — is the identical advisory-accumulation shape already found in the Vibe Marketing Playbook's Brand Memory, skilltune's eval scoring, and @skills' AI Boost rating. Four different, unrelated companies, all building "gets better through use," none building deterministic verification against a specific rule.

Open technical question, not assumed to work: `check_compliance` verifies code deterministically — a regex catches a hardcoded hex value with certainty. Verifying whether a generated video frame or ad image actually matches brand rules is a fuzzier, likely computer-vision-based problem — a real capability gap, not a natural extension of what's built.

Sharpened 2026-08-14 — the mission stated plainly, using the framing that prompted this: "the brand Swiss Army knife." Not "Tastefield does everything a creative director or agency could do" — a creative director's replaceable work is production, increasingly already handled by Higgsfield, Motion, and Toolcraft. Their irreplaceable work is judgment: does this match the brand, regardless of who or what made it. A Swiss Army knife isn't valuable because it replaces a table saw — it's valuable because it's the one small, sharp thing that's useful everywhere. That's the correct shape here: not a bigger tool that does more, but the same one — brand judgment — showing up in more places: code, video, ads, websites, motion graphics, via the one generalized brand-rules tool above. Building the production side back in would undo the discipline the rest of this section already argues for.

**Phasing for the vertical creative-director ambition (2026-08-15).** Split by what costs engineering time versus what costs conversation time, since those don't have to be sequenced against each other:

- **Stage 0, now, parallel with Phase 1.** Structured domain research, not casual conversations: interview or shadow 5-10 real creative directors/agency leads, spread across the registry's existing categories (fintech, consumer, SaaS, devtool, healthcare) for coverage. Capture where they actually intervene or reject work and why, how they defend a brand decision to a client, what triggers a real revision cycle vs. noise, what's tedious vs. needs real judgment. Write findings directly in the Trigger/Decision/Reason/Evidence/Trade-off format already adopted — usable immediately as sourced restraint content for near-term registry recipes, not just background research for later. Pays off even if Stage 3 never happens. Compensate people properly for their time. Explicit pipeline, 2026-08-15: these interviewees are the natural first creators for the registry's new "Recipes by role" section specifically — a creative director interviewed for Stage 0 research is the obvious first author of the actual `creative-director` recipe, not just a source quoted inside it.

  **Allocation principle, 2026-08-15: spend interview time only where a research-and-synthesize workflow can't reach.** Real pattern already in practice elsewhere: research a domain via Perplexity, feed it to Claude Code, generate a skill from published theory (classic copywriters, modern DTC principles), refine by testing against real outputs — fast, and genuinely good at capturing published, generalizable theory. It cannot reach the thing Stage 0 exists for: not general theory, but the undocumented, situational judgment that only exists in one person's head — why a specific creative director rejected a specific piece of work, the pattern behind that call. Directly relevant to the risk already logged above: the whole Stage 0→2→3 chain assumes tacit judgment converts into generalizable rules; capturing only the theory layer gets the easy 80% and misses the point. Also sharpens, not undermines, the earlier @skills finding — a workflow like this crowds the generic hand-authored lane further, making Stage 0's real-sourced content matter more, not less. Practical rule: don't spend scarce interview time on ground a research-and-synthesize loop already covers well; reserve it for the reject/approve reasoning and client-defense patterns nothing published captures.

  **Capture guidance, 2026-08-15, from "Design Is How It Tastes" (see Studio, DESIGN.md critique): preserve encounter-language, don't compress it into tokens too early.** If a real creative director's actual reasoning is closer to "this feels like it's trying too hard" than "the padding's wrong," write down what they actually said, not an immediate translation into token-speak. Deepens the same differentiation the allocation principle above protects — real, sourced, embodied reasoning is exactly the "compiled history with real corrections" already named as one of the four things that resist fast-following, and compressing it early loses the same signal the essay describes losing from design specs generally.

  **Public delivery mechanism, 2026-08-15: a podcast, "General Creativity."** Not a separate idea from the research above — the same Stage 0 interviews, recorded and released, doing the research and building audience from one effort instead of two. First guest deliberately chosen: someone excellent at podcast production, interviewed about podcasting — direct-sourced material for the podcast-producer role recipe's Phase A (sonic branding, mastering, show-notes voice), not just a good opener. Same scope caution as Machinekind: stays a strength if it tracks Stage 0's actual research cadence; becomes a liability if it grows into its own production commitment independent of that.

  **Priority against the marketing site, and where it lives, resolved 2026-08-15.** The marketing site comes first, clearly: the actual moat is real accumulated customer use — real compiled histories, real corrections — and the site is the direct path to converting interest in the already-working Phase 1a into that real usage. The podcast produces research and incidental reputation, both real, but reputation is a slower, longer-horizon asset than real customers using a real product, and it doesn't itself generate the thing just identified as durable. Site placement follows the same test as the scope caution above, made explicit: if the podcast stays tied to Stage 0's original purpose — real creative directors and agency leads, sourcing real recipe content — it belongs close to Tastefield, linked directly from the site, legibly Tastefield's own research happening in public. If it grows into "any skilled knowledge worker learning about creativity broadly," that's the same "medium empire" risk already flagged for Machinekind, just relabeled — a real, different, bigger project that would dilute Tastefield's own positioning rather than support it. Default: scoped and integrated now, standalone only as a deliberate later decision if Stage 0's research genuinely outgrows what the site can hold — not assumed upfront because the bigger version sounds exciting.
- **Stage 1, already in motion.** Prove the rules engine — Phase 1 finished, Machinekind as the real-world proof it works.
- **Stage 2, built on Stage 0 + Stage 1.** Role-specific recipes (creative-director, social-media-manager, podcast-producer — the taxonomy extension proposed 2026-08-15), now backed by real domain research instead of a plausible guess.
- **Stage 3, only once 1 and 2 are proven and demand is validated — deliberately last, still unphased.** An owned creative-director agent, differentiated by native compliance built into the generation loop rather than a rules file a third-party agent might or might not read closely — the edge identified against Hyperagent. Competing with Hyperagent directly isn't ruled out here — it's sequenced, not rejected.

  **Design discipline required if this proceeds, 2026-08-15: no bundled proprietary recipe.** An owned agent shipping with its own free, in-house `creative-director` recipe cannibalizes the marketplace directly — nobody buys a creator's version when the default is free and comes from the platform itself, undercutting the trust the Bradley-Terry blind-voting system exists to protect. The owned agent must source its default recipe from the same open leaderboard everyone else competes on — winner of the public vote gets the slot, Tastefield's own entries included and not identity-protected any differently than anyone else's. Turns the conflict of interest into a public demonstration the marketplace actually works, rather than a reason to distrust it.

  **Real cost, worth deciding with eyes open: this converts Hyperagent from partner to competitor.** Hyperagent is logged in this section as a confirmed consumption point for the generalized brand-rules tool — a fleet whose agents would read Tastefield's rules. An owned creative-director agent goes head-to-head with Hyperagent's own instead. Higgsfield and Motion are mostly unaffected — generation infrastructure, not orchestration, a different category — but Hyperagent specifically loses partner status if Stage 3 happens. Not a reason to avoid it; a cost that shouldn't be discovered after the fact.

**Adjacent bet, not a new consumption point: turning any archive into an agent tool (2026-08-18, from a startup-ideas video segment, "Expert Archive to Agent Tool").** A different pattern than the seven consumption points above — instead of a generator reading Tastefield's rules, the archive itself becomes the compiled thing. The pitch: pick an expert with a deep archive and a narrow audience, transcribe/tag it, ship one job-specific workflow (paste X, get a cited, scored, structured Y), monetize per-use rather than via ads. Whether this belongs inside Tastefield turns on one filter, not enthusiasm for the pattern: the domain axis. A sales trainer's or real-estate expert's archive isn't visual/brand/copy/motion/architecture/content/conversion/process — building it inside Tastefield would be exactly the "widen the category, become a worse mirror of skills.sh" failure mode non-negotiable #4 and the Taskmarket domain-axis discipline (Roadmap reframe, below) both already warn against; it's a separate product on a shared, licensable engine (scan → compile → check → MCP), not a Tastefield feature. A design/brand/copy/motion/conversion creative's archive is different — already inside the existing domain taxonomy, and "populating the copy/content/conversion side of the existing axes" is already the named gap, not new scope. But even there, check the buyer before the domain: Tastefield's core product is defensive (you have a system, stop AI from drifting off it); this pattern is generative (you have no taste, you're importing someone else's) — the identical opposite-direction-on-the-same-axis relationship already drawn against GetLayers above. Concretely: hostable in the Public registry as a distinct "guest recipe" subtype (see recipe taxonomy below), never silently merged into the "extract and enforce your own system" recipes it sits next to.

  **Monetization pattern, same source.** The archive's raw content is usually already free (a YouTube video costs nothing to watch) — what's actually sold is the compiled, tagged, cited judgment layer on top of it, the same reason brand/copy rules were already said to outlast visual ones ("Two axes," above: base models won't independently know a company can't say "cheap"). Two different buyers need two different pricing shapes: an occasional human user wants a single metered result, not a subscription; a downstream builder or agent wholesaling the expert's judgment into its own product is the real x402 case (Roadmap reframe, below) — an autonomous caller with a budget, not a human filling out a checkout form.

Status: vision, not roadmap. No phase number, no committed work. Don't let this bleed into Phase 2/3 descriptions until it's actually decided.

## Open questions — not decided, don't build against these

- **Should Tastefield recipes be discoverable through @skills' open protocol, not just the registry and MCP server (2026-08-15)?** The extensible source-connection list and the agent-readable setup file idea were both decided on the same logic — ship broadly, don't pick one channel. @skills (atskills.one, see Competitive landscape) already has a "design visual" category with 60,000+ skills referenced through it — being present there is a reach question, not a governance question, since the compiled, checkable rule underneath a recipe stays exactly what it is regardless of which channel surfaces it. Not decided: whether packaging recipes for a second, general-purpose discovery layer is worth the effort before the registry itself has any real content in it.
- **Same question, second channel: should recipes be shadcn-CLI-installable (2026-08-15, from beUI, firmed up 2026-08-15 by agentcn)?** shadcn's CLI has become an open registry protocol beyond shadcn's own components — beUI (see Studio, fifth source path) distributes entirely through it. A concrete technical shape already exists to copy rather than invent: beUI exposes plain, agent-readable endpoints per component (`/r/{slug}.json`, `/r/{slug}/raw`, an `llms.txt` index) so coding agents can read without scraping the UI — the same pattern a `@tastefield/fintech-trust-first` recipe could follow, `npx shadcn add`-able like any other registry item. No longer speculative: agentcn (see Competitive landscape) is shadcn-labs' own extension of this exact registry format beyond components into full composed patterns, `npx shadcn add @agentcn/eve/deep-search` — the same ecosystem beUI publishes into, actively building toward exactly this shape. Same reach-not-governance logic as the @skills question above; not decided whether to build either, both, or wait until the registry has real content to distribute.
- **Hosted Recipe API (`mcp.tastefield.com`)?** Raised in 2026-08-13 strategy sessions: a live endpoint that lets a third-party app (e.g. one built with Pixel Point's Toolcraft) fetch brand rules at runtime and merge them into end-user prompts before hitting an LLM. This is content governance for end users, not code governance for developers — a different product surface than anything built today. It also cuts directly against non-negotiable #1 (no telemetry, nothing sent anywhere, local-only) — not because it's telemetry, but because a queryable network endpoint is a different trust model than "runs on your machine, phones home to nobody." Don't build this without explicitly revisiting whether "local-only" is a permanent constraint or a Phase-1-only one. If it proceeds, it should be its own roadmap phase, not a sub-bullet under a GTM idea. Context.dev's credit-metered pricing (see Competitive landscape below) is a concrete reference point if this moves forward, rather than inventing pricing from scratch. Implementation option, 2026-08-14: Monid (monid.ai) already brokers per-call payment and agent-discovery for 1,300+ third-party tools — listing Tastefield as a provider there is a third path alongside "build it" and "don't," avoiding bespoke payment/metering infrastructure. Early-stage (v0.1.0) — worth knowing, not worth betting real integration work on yet. Access shape, 2026-08-15, from Vessa: split read from write cleanly if this ever proceeds — unauthenticated, no-login read (a public JSON an agent fetches directly) versus authenticated write requiring human oversight. Read is the low-risk half; write is where the non-negotiable #1 tension actually concentrates.

  **Real-world confirmation of the underlying tension, 2026-08-18 (see Carl Sziebert's ux-agent-skills, Competitive landscape).** A skill that executes entirely inside the buyer's own agent has no server in the loop for x402 to meter — the identical local-only-vs-hosted-endpoint fork this bullet already describes, just showing up in a different, adjacent product instead of staying hypothetical. If Tastefield's own recipes ever ship for local, in-agent execution *and* a hosted, agent-callable verification/fetch API, keep the two surfaces deliberately separate (free/open local path, metered hosted path) rather than assuming the free path funds the paid one automatically.
- **Does `src/scan/` extract from a live URL, or only a repo?** Both the Specimen Wall hero (paste `stripe.com`, watch tokens extract) and the registry's real-company recipe variants (see below) assume Tastefield can point at an arbitrary live site and pull its tokens. That's a different pipeline than parsing CSS/cva out of a repo someone gave access to — DOM/rendered-CSS scraping vs. source parsing. Confirm this exists, or scope it, before committing further to either. Buy option, 2026-08-14: Context.dev's `/web/extract` (arbitrary JSON-schema extraction from any URL, JS rendering and anti-bot handling included, $25/mo Developer tier) could power this without building scraping infrastructure from scratch. Real tension worth deciding on purpose, not backing into: this would make a hero demo and a sourcing lane depend on a company also listed as a competitor below — ongoing cost and vendor dependency, not a one-time build decision. Build option, also 2026-08-14: tastelab.xyz — a free, single-developer Claude Code/Gemini CLI skill — does exactly this with Playwright MCP (scrape a live rendered site, extract tokens + reasoning). Real evidence the capability is buildable by one person, not just purchasable from a funded vendor.
- **Agencies as the customer, or bypassed?** Phase 3, as it stands, is built entirely on agencies being the buyer — multi-tenant dashboards, the CI/CD bot sold as their retainer. The "one creative director + a fleet of agents" idea in Vision points a different direction: a director going direct, no agency needed. These aren't automatically compatible — different buyer, different sales motion, possibly different price point. Three real options, not yet chosen: serve agencies as planned; go direct to brands instead; or treat them as genuinely separate tiers (agency-facing governance tool vs. a lighter direct-to-director version) rather than one blurry pitch covering both. Adobe Brand Intelligence's own positioning — "especially valuable if your organization navigates many agencies" — suggests a fourth option worth naming: sit above the agencies, sold to the brand, not to the agency or instead of one. See Competitive landscape.
- **Rendering real components from a Local/GitHub codebase, when there's no third-party tool to defer to (2026-08-15) — flagged, not just scoped.** Legitimate case: the Storybook boundary in Studio explicitly says don't rebuild what Storybook already does — but that only holds when Storybook exists. Someone with no third-party rendering tool at all isn't being replaced, there's nothing there to replace. The problem is what rendering actually requires: importing and executing a customer's real component code, which is a materially different capability than `src/scan/`'s current static parsing of CSS/cva — and it runs directly into the reasoning behind non-negotiable #6, not just its literal text. That non-negotiable is scoped to Tailwind configs specifically ("running arbitrary code from a scanned repo is a security problem"), but the same reasoning applies exactly to executing arbitrary component code to render it. Not ruled out — Storybook, CodeSandbox, and StackBlitz all solve this with heavily sandboxed execution (no network, no filesystem, isolated runtime) — but it needs that same deliberate sandboxing if pursued, not a casual assumption that scanning and rendering are the same kind of operation.
- **The market's load-bearing assumption: governance stays separable from generation (2026-08-15) — the one risk without an execution fix.** Every player in this landscape, Tastefield included, assumes you can bolt judgment onto someone else's generation engine rather than needing to own generation yourself. That assumption is already under pressure from both directions at once: Adobe's brand brain already learns continuously from every reviewer decision, not just an initial upload; Taste Labs already sells "give frontier labs taste" directly to the labs, not just to app-layer companies. If a frontier model starts absorbing company-specific taste natively — ingesting a connected repo at session start, the way `check_compliance` reads one now — the standalone compiled layer gets squeezed from both ends: the model gets better at this on its own, and generation platforms (Higgsfield, Hyperagent) build the same capability directly into their own product. Unlike the other open questions above, better sequencing or scoping doesn't fix this one — it's a real bet on the market's shape, not an execution risk.

  **A concrete instance, closer than a frontier lab, 2026-08-15: zeroheight.** Not hypothetical absorption by a model — a real, massive, enterprise-embedded incumbent (20% of Fortune 100, Uber and Decathlon named customers) already moving hard into "agents build from your design system" positioning, with a live MCP server and Claude/Cursor already in their own integrations bar. The honest version of the moat question, stated plainly rather than assumed away: `scan`/`compile`/`check`/MCP is exactly the kind of thing AI makes cheap to rebuild, and zeroheight already has the distribution, enterprise trust, and AI-agent positioning a from-scratch competitor would need years to earn. What still holds, and it's the same distinction as the Medium design-lead source: zeroheight's core mechanism is human-authored, human-maintained documentation served to agents, not automatic extraction from live shipped code — a real, structural difference, not just a head start. What doesn't fully hold: the belief that the engine alone is safe just because it's technically differentiated today. Durability has to come from what accumulates on top of the engine — a real customer's compiled history with real corrections, real Stage-0 relationships, public Arena reputation, Machinekind actually proven — not from the engine remaining hard to copy indefinitely, because it won't.

  **Companion evidence, both directions, 2026-08-15.** A real, live "AI memory portability" ecosystem already exists — Mem0, MemoryLake, and notably Supermemory, an MCP-based memory graph connecting ChatGPT/Claude/Cursor in one setup — the exact same delivery mechanism Tastefield already bet on, independently arriving at the same architecture for a different kind of context. One piece of enterprise research on this space (Atlan) states Tastefield's own reason to exist almost verbatim: "MCP standardizes how agents connect to data and tools. It does not, by itself, certify that the definition being delivered is current or approved." External validation that the pipe (MCP) and the guarantee (compile + check + curation) are genuinely separate problems, not the same one. But it cuts both ways on the absorption question above, worth holding as a real, unresolved tension rather than picking a side: if the market converges on open, vendor-neutral portable-context standards, that's hospitable ground for a standalone compiled layer to keep mattering. If it converges on frontier models and generation platforms absorbing this natively instead, that's the squeeze described above. Both are live possibilities right now.

  Difficulty, broken down: isolation itself is the easy part — integrate an existing sandboxed runtime (StackBlitz WebContainers, CodeSandbox Sandpack) rather than building container infrastructure from scratch. Dependency resolution is the actual hard part — an arbitrary customer's real repo (node_modules, peer deps, monorepo path aliases, custom PostCSS/Tailwind config) is a much harder build target than a clean demo repo, and this is typically where effort actually goes, not the sandboxing itself. Sample-prop inference for a meaningful render is a real but smaller third problem. Ongoing cost, not one-time: both WebContainers and Sandpack's own operators have had real sandbox-escape issues historically — this is a standing security commitment, not a box to check once. WebContainers also carries a commercial license at real usage volume, not free to embed at scale.

  Staged path, avoids committing to the hardest version first: if a customer already has Storybook, embed their existing static Storybook build — zero arbitrary execution, sidesteps the problem entirely for that subset. Reserve WebContainers/Sandpack for customers with no Storybook at all, which is the actual case this question is about — lets the harder investment wait until it's clear how many customers need it.

### Taste Arena — mechanics detail

**Task viability, learned from Taskmarket's own live data (2026-08-14).** Their open tasks sit at mostly zero bids despite 19.5K registered agents — visible evidence of what makes a listing dead on arrival. Three criteria a listing needs to clear: (1) a real, checkable win condition ("build the `neobank` variant of `fintech-trust-first`, passing these five `check_compliance` rules" — not "make a living world in six seconds"), (2) reward proportionate to effort (their 0.008 USDC tasks are a rounding error with a headline, not an incentive), (3) reaching a narrow, relevant audience rather than a firehose a specialist has no reason to scan. Fill-a-variant-gap, improve-a-weak-recipe, and propose-a-6th-category all clear this bar today.

**Self-generating bounties from passive detection — the actual fix for Taskmarket's liquidity problem.** Three signals generate a listing with no human authoring it: taxonomy gaps (an empty category/variant cell), coverage gaps (`check_compliance` hitting a pattern with no matching rule, across real projects), and weak/stale recipes (`src/bench/` density worse than siblings, or a lane-1 source guide that's since changed — watchable via something like Context7's Monitors feature, which watches any URL for changes). Rewards pool rather than being funded per-listing: every time the same gap gets detected again, a small amount adds to a standing reward for that gap, growing on its own until someone fills it. Maps onto Taskmarket's own modes: Claim mode for taxonomy gaps (first qualified agent reserves it, guaranteed pay for qualified completion), Benchmark mode for weak/stale recipes (`check_compliance`/`src/bench/` auto-score the improvement, a human only breaks ties). Funding: a slice of the Phase 3 agency retainer could seed a base pool per category; if the hosted Recipe API question resolves yes, a sliver of each paid fetch could route back in. One real tension, not optional: the coverage-gap signal means something leaves a customer's local scan to inform a public pool — needs to be opt-in and genuinely anonymized (a category label, never code or project identity) or it shouldn't feed the pool at all, per non-negotiable #1.

**Stay bounded to the existing domain axes — don't widen the category.** Taskmarket's own task list (worldbuilding video, game restaging, crypto referrals, PR merges) is a cautionary example, not a template: a market with no natural source of its own demand takes whatever it can get. The self-generating-bounty mechanism above already solves the liquidity problem within a narrow niche, which is a better answer than going broad. Room to grow exists *within* the domain axes already defined in "Two axes, deliberately not merged" (visual, brand, copy, motion, architecture, content, conversion, process) — copy/voice tasks, accessibility-audit tasks, motion-spec tasks — all still squarely design/dev, none of it general-purpose gig work.

**"Beyond design" clarified, 2026-08-15: build what's already named, not a new scope.** The domain axis was never design-only — copy, content, conversion, and process are already listed and already legitimate. Almost every concrete example built out so far (fintech-trust-first, saas-dense-dashboard) leans visual/brand-heavy simply because that's what got built first, not because the taxonomy is narrower than it looks. Expanding "beyond design" means actually populating the copy/content/conversion side of the existing axes, not deciding to cover new ground.

**A second, usage-based leaderboard, distinct from the creator one (2026-08-14, from Context7's Rankings page).** Not creator reputation — real usage: which registry categories/variants actually get queried by real agents, and which coding tools (Claude Code vs. Codex vs. Cursor) pull from Tastefield most. Serves two jobs: a public trust signal ("real usage, not vanity metrics"), and a live prioritization signal for the self-generating bounty mechanism above — a category queried constantly with no filled variant is a stronger bounty candidate than one nobody's asked for yet.

**A public submission-review gate, distinct from ranking (2026-08-15).** Bradley-Terry voting answers "which of these is better" — ranking among things already in the pool. A different question needs its own mechanic: "should this specific submission be accepted at all." Borrowed pattern, generalized from the pull-request mechanic — propose, becomes visible, feedback attaches directly to specific parts, async inspection, approval changes an explicit state, the whole thread persists afterward. The public counterpart to Studio's private compiled-draft review, not a duplicate of it. Built triage-first by design, not as an afterthought: `check_compliance` screens every submission before a human ever sees it, and only what's compliant-but-judgment-worthy reaches a review queue. Reason this matters from day one, not later: this exact mechanic is currently buckling under AI-generated volume in its own home domain — LinearB's 2026 benchmark (8.1M PRs) found only 32.7% of AI-assisted PRs merge within 30 days against 84.5% of manual ones, reviewer pickup time up roughly 5x, and a separate study found 61.38% of agent-authored PRs receive no recorded review at all. The reason given: "review was designed around writing being expensive... that assumption is what's gone." The Arena already anticipates agent-submitted volume (see creators, above) — adopting this mechanic without automated triage first would hit the identical bottleneck, not a hypothetical one. Second triage layer, 2026-08-15, from The Vibe Marketing Playbook's "Expert Review Framework": spin up 3-5 specialized reviewer personas (a brand-voice specialist, an accessibility specialist, a category-specific expert), each reviewing independently, synthesize where they agree — a real, reusable pattern for stretching human review capacity without just adding more humans. Sits between `check_compliance`'s deterministic pass and the human queue, not a replacement for either.

**Why anyone actually submits, 2026-08-15 — has to outweigh a real cost, not just list upside.** Money: recipe sales (Aura-style, $29-39/template), bounty payouts for filling a detected gap, usage-leaderboard visibility creating demand for whoever fills a category first. Reputation as a checkable portfolio, not a claimed one: the dual leaderboards function the way open-source contributions function for engineers. A pipeline to real paid work outside the platform entirely — Taste Labs' actual TasteMakers program already runs on this exact mechanism, "paid projects... no middleman markup." A separate, different-shaped incentive if it's a company publishing its own compiled system rather than an individual creator: closer to why companies publish open design systems today (Polaris, Carbon) — credibility and recruiting, not marketplace income. All of this has to outweigh the real cost of exposing work, which is exactly what the paid/free mechanism below exists to offset.

**Differentiated from Design Arena, 2026-08-14 — same proven mechanic, different axis.** Design Arena runs blind pairwise voting, Bradley-Terry rated, at real scale (5.1M+ users) — but it ranks *foundation models* against each other, not recipes or creators. Reuse the mechanic exactly, change what's being compared: two Tastefield recipe variants applied to the same generation task, blind, voted head-to-head — "which governance produced the better on-brand result," not "which model is best." Two things neither Design Arena nor Taste Labs (see Competitive landscape) can do, because neither has an enforcement engine underneath: (1) a dual-axis leaderboard — Taste (the crowd vote) alongside Compliance (an objective `check_compliance`/`src/bench` score against the category's actual rules), not vote-only; (2) votes settle real money, not just a benchmark score — a match-up is literally two candidates for a specific taxonomy gap, and the winner collects whatever's pooled in the self-generating bounty above, wiring the vote directly to the marketplace instead of leaving it as a side metric.

**Compliance compounds with proven use, not a one-time gate score (2026-08-15) — reputation as a byproduct of normal use, not extra work to contribute.** This is the same mechanic already running elsewhere in this file, just not previously named as one: "when a creative director rejects output and says why, that correction becomes a candidate restraint" is reputation-as-byproduct applied to rule quality — nobody does extra work, the correction was happening anyway. Applied here: a recipe's Compliance score shouldn't stay a one-time gate check from submission. A recipe used cleanly across real deployments with zero corrections needed is a more trustworthy artifact than one that merely cleared the bar once — the marketplace principle that every clean transaction should make the next adopter's decision easier. Respects non-negotiable #1 by reusing an existing pattern rather than inventing a new tension: opt-in and anonymized, the identical shape already governing the bounty system's coverage-gap signal. A clean pass reports anonymously if opted in; no opt-in, no signal, no penalty either way.

## Landing page hero — "Specimen Wall" concept (Phase 2, not built)

Decided 2026-08-13. Replaces a "single button re-styles" demo — that reads as a CSS trick and doesn't prove the engine extracts systemic design tokens rather than one color value.

Default state (no URL pasted) is the animated before/after loop described below, not a static one-time state. **Before/after mechanic (decided 2026-08-14).** Applies to the wall itself, not a dashboard. A dashboard is one coordinated composition — if its colors change, that reads as one hand-tuned screen. A wall of unrelated primitives (pricing card, form, table, modal) has no structural reason to look coordinated; watching all of them snap together at once is what proves "systemic" in the first place — putting the before/after on a dashboard instead would undo that reasoning.

The "before" state carries violation callouts, not just worse styling — small tags pointing at what actually got caught (a hardcoded hex value, a hallucinated prop, a missing confirmation dialog on a destructive action). Makes the demo about compliance/hallucination-prevention (the messaging shift already decided, see Roadmap reframe proposal) rather than a theme-switcher.

Interaction, ordered by ascending effort:
1. **Auto-pulse.** The whole wall cross-fades between governed/ungoverned on a slow loop (3-4s), unprompted, on page load.
2. **Single drag handle.** One vertical wipe line across the entire wall, not per-card sliders — dragging it reveals the other state at the same x-position across all components at once, so the motion itself reads as coordinated.
3. **Click to pin.** Click any card to freeze it and read its violation callouts individually.

Related idea, deliberately kept separate: two agents (governed vs. ungoverned) building the same spec live, side by side. Compelling but slow and expensive to run live — scoped as a recorded case-study video, not hero-page real estate.

Corrected 2026-08-15: DESIGN.md isn't just a convention Refero and Aura happened to converge on — it's an actual specified format from Google Labs (`github.com/google-labs-code/design.md`), the same spec Google Stitch and tasteprofile.io use. Target the real spec for Studio's export, not a lookalike.

**A real critique of DESIGN.md itself, worth holding precisely rather than deflecting (2026-08-15, from "Design Is How It Tastes," superposition.jem.computer).** Names DESIGN.md directly: "sound idea... but read a typical DESIGN.md and you will find language like 'use 8px radii, use a neutral palette' — useful, but thin. It describes the produced object. It does not preserve the intended encounter." Draws a real distinction — object-language (describes the artifact) versus encounter-language (describes the felt experience of meeting it) — and argues encounter-language is precise along a different axis, not just vaguer-but-nicer, and that diffusion models can now generate form from it directly. Lands a genuine hit on `scan`/`compile`'s token-extraction and on DESIGN.md as the target export. Resolved, not dismissed: the essay's own proposed flow is "sensation → visuals → system... only after a design tastes right do you derive tokens" — tokens still get derived, just downstream of the feeling, not the starting spec. The critique lands hardest on DESIGN.md used as a *prescriptive starting brief* — exactly how Higgsfield, Motion, and agentcn's "Extract DESIGN.md" already use it, all three already flagged this session for guessing from a live read. Tastefield's version is a *compiled record* of decisions a real company already made and validated — the why already happened, embodied in a shipped product, whether or not the compiled file says so in words. Same file format, structurally different use — not the same critique.

**A second, more technical critique — modular, indexed export instead of one monolithic file (2026-08-15, from "How to Make Your Design System Agent-Ready," a real enterprise design lead, 2 days old).** Independently converges on the same Google Labs `design.md` spec already targeted, then goes further: don't export one giant file — structure it as `tokens.json` (styling foundations) → `design.md` (global conventions) → `components.md`/`patterns.md`/`templates.md` as **registries**, each pointing to individual `*.component.md`, `*.pattern.md`, `*.template.md` files. Her own reasoning, worth adopting directly: "the agent can retrieve the context relevant to the task instead of loading the entire design system every time — keeps the information easier to maintain and avoids consuming context unnecessarily." Reinforces the get-everything-tool restriction already in non-negotiable #1 with a concrete efficiency argument, not just a philosophical one. Concrete refinement to Studio's export target: build the DESIGN.md compile step toward this indexed hierarchy, not a flat file, from the start.

**The sharpest available validation of why `scan`/`compile` exists at all, from the same source.** She draws a precise line — tokens solve styling, not structure or behavior: "a token file doesn't tell the agent that our Wizard consists of a Top Bar, Stepper, Header... which actions belong where, how navigation works." Real, concrete content for the Architecture domain (see build-order priority below) — composition rules and behavioral contracts, not just an abstract "engineering judgment calls" placeholder anymore. And her own closing admission is the single cleanest piece of validation found this session: "who maintains all of these specifications? The answer shouldn't be designers manually updating Markdown every time something changes in Figma... probably a topic for another article." A real practitioner independently designed almost exactly the right structure, then named the one open problem she hasn't solved — and it's precisely what `scan`/`compile` already answers: automatic extraction from a live source, not manual authoring.

Explicitly not a Pinterest-style discover/follow feed of other people's UI (that's buildwithtaste.com's actual business — personal taste aggregation, not documenting an existing brand's real decisions — see Competitive landscape). Same lesson, correctly scoped: useful for justifying a decision, not for browsing inspiration.

Also flagged from that mockup: the recipe panel's skill tags (GUARDRAIL, VOICE, VISUAL, BRAND) show one badge per skill. That contradicts "Two axes, deliberately not merged" above — domain and category are separate, and skills are frequently multi-domain. ## Public registry — recipe taxonomy (Phase 1, not built)

Decided 2026-08-13. Recipes are browsed by product category, not by company name — a visual-only recipe like `linear-vibe` has no story; a real recipe (tokens + negative restraints + voice rules) does.

Naming: category-first, named for the problem solved — `fintech-trust-first`, `consumer-checkout-safe`, `saas-dense-dashboard`, `devtool-dark-first`, `healthcare-intake-careful`. Legible in ten seconds without recognizing a company.

Each category has variants, not one monolithic recipe. Example:

```
fintech-trust-first
├── institutional  — "boardroom conservative"  — navy/charcoal, dense tabular numerals, minimal motion
├── neobank        — "confident and modern"    — high-contrast mono type, one bold accent, generous whitespace
└── embedded       — "invisible and fast"      — near-zero chrome, built to disappear inside someone else's product
```

The mood caption ("boardroom conservative") is the picker — people choose a variant by vibe, not by reading a token table first. Presentation pattern borrowed from Refero's mood-caption style (see Competitive landscape) — not their data. Enrichment, 2026-08-15, from "Design Is How It Tastes" (see Studio, DESIGN.md critique above): the existing captions are object-language wearing a vibe label — "high-contrast mono type, one bold accent" describes the artifact, not the encounter. Pair each variant with a genuine sensory line alongside the existing description, not replacing it — the hush before a decision gets made, not the mono typeface — a natural extension of the picker's own stated purpose, not a new direction.

Confirmed 2026-08-15, against tasteprofile.io: a recipe page is meant to do double duty — human-browsable (mood caption, visual specimen) and agent-fetchable (DESIGN.md/tokens export) from the same one artifact, not two separate deliverables. tasteprofile.io's own hosted-viewer pitch is the identical shape, arrived at independently — good confirmation this is the right structure, not a course correction.

**A second, cross-cutting taxonomy dimension: role, not just product category (2026-08-15, from Hyperagent).** Everything above organizes recipes by what's being built (`fintech-trust-first`, `saas-dense-dashboard`). Hyperagent ships a named fleet of role-specific agents — creative director, social media manager, podcast producer — with no visible brand-governance layer behind any of them. A recipe scoped to *who's* building, not just what's being built, is a different, real thing: a `creative-director` recipe governing high-level brand-consistency judgment calls, a `social-media-manager` recipe governing caption voice and platform constraints, a `podcast-producer` recipe governing audio branding. Same compile-and-serve architecture, organized by role instead of output type — and it's what any of Hyperagent's own fleet agents would read from, making Hyperagent a plausible consumption point for the generalized brand-rules tool (see Vision), the same relationship already established with Higgsfield and Motion.

**Two separated sections in the registry, not one mixed list.** "Recipes by product category" (fintech-trust-first, saas-dense-dashboard, etc.) and "Recipes by role" (creative-director, social-media-manager, podcast-producer) answer different questions and get browsed for different reasons — mixing them recreates the exact "seems random" failure the category-first taxonomy was originally designed to fix.

**A third registry shape, flagged 2026-08-18, not yet a decided taxonomy addition: "guest" or borrowed-taste recipes.** Distinct from both category recipes (your own system, extracted) and role recipes (judgment for a role adjacent to your system) — a compiled archive belonging to a named individual creator (a brand critic, a copy specialist, a motion designer), sold or bountied as its own product, e.g. "run this ad through [critic]'s voice rules." Same domain × category tagging, same Trigger/Decision/Reason/Evidence/Trade-off restraint format, same Free/Paid gating already specced above — reuses the mechanism entirely (see the archive-to-agent-tool discussion in Vision). Kept a separate label rather than folded into either existing shape on purpose: category and role recipes both extract and enforce a real company's *own* decisions; a guest recipe imports someone else's taste on purpose — the same opposite-direction relationship already drawn against GetLayers in Vision. Mixing the label would blur that distinction the same way mixing product-category and role recipes into one list was already ruled out just above. Not decided whether this ships at all — flagged for whenever the registry has real category/role content first, per the same sequencing discipline already applied to the Arena and x402.

**Site IA question raised and resolved 2026-08-18: should "design system," "recipe," "skill," and a generic "styling / look and feel" section each be a separate, equal-weight top-level site section?** Two of the four already are, for a real structural reason, not just sequencing: Studio (design system — connect or start your own) and this Public registry (recipe — browse compiled, curated bundles) answer "build mine" versus "browse everyone's," and are already different phases (2 and 1) because of that difference, not by coincidence. A third, equal-weight "Skills" section was considered and declined: a skill is the uncurated unit underneath a recipe (non-negotiable #4, `src/registry/`'s skills.sh sweep), and a standalone browsable skills page would compete with @skills' own 60,000+ free index instead of showcasing curation as the actual differentiator (see Competitive landscape). Skill visibility belongs nested inside a recipe's detail page instead — the same fix the skill-tag-badge issue in Studio already needs (render both axes per skill, not a single collapsed tag). A fourth "generic styling / look and feel" section was also considered and declined, for the same reason the fifth-path template shelf in Studio already stays deliberately bounded: it's that shelf's entry point, not an independently-maintained taxonomy axis — the exact sprawl risk "not a fourth taxonomy axis... which would sprawl into independent maintenance nothing here needs yet" already named above.

**Podcast-producer, phased rather than narrowed (2026-08-15).** Full podcast production is the widest reach of the three role recipes — closer to general content-ops than the domains already named (visual, brand, copy, motion, architecture, content, conversion, process). Rather than permanently capping scope, phase it the same way Stage 3 of the creative-director ambition is sequenced: **Phase A, maps cleanly to existing domains** — intro/outro sonic branding, audio mastering consistency, episode cover art tokens, show notes and titling voice. **Phase B, full episode production** (assembly, editing, guest workflows) — deliberately last, unphased and undecided until Phase A is proven, not ruled out.

**Explicit pricing field and gating mechanism, 2026-08-15 — makes the preview-public/source-gated split from 2026-08-15 concrete, not just conceptual.** Every submission declares Free or Paid ($price) explicitly at submission time — no ambiguous default, the same explicit-over-implicit discipline already applied elsewhere in this file. What's gated tracks the existing double-duty recipe page exactly: the human-browsable half (mood caption, visual specimen) is always public regardless of pricing, since Bradley-Terry voting and browsing only need it and gating it would break ranking integrity. The agent-fetchable half (the actual DESIGN.md/tokens export, the installable content behind `npx --recipe=X`) is what the Paid flag gates — returns a "purchase required" response instead of the real content until bought. Marked Free, that same half is returned automatically, no purchase step, no separate mechanism — identical to today's behavior. Default posture: Free unless a submitter explicitly opts into Paid, matching the registry's generally open ethos rather than accidentally gating something meant to stay open. Which lane should lean which way isn't arbitrary: hand-authored generic recipes are the ones already found exposed to @skills' 60,000+ free alternatives (see Competitive landscape) — natural Free candidates, competing on volume and visibility rather than a price nothing justifies. Real-company-sourced and Stage-0-role-sourced recipes are the natural Paid candidates — uniquely valuable, not freely available elsewhere, genuine pricing power. Related but distinct infrastructure need, not automatically solved by it: this is read-gating for a specific paid recipe, different from the authenticated-write access split already flagged for the hosted API question in Open questions — likely shares underlying auth, but worth tracking as its own requirement rather than assuming one covers the other.

Sourcing, per variant — four lanes:

1. **A real company's own publicly-published guide** (companies that release brand/style guides for external reuse — press kits, partner docs), generalized to a principle and credited on the recipe's detail page ("neobank variant modeled on Mercury's public design guidelines"). Shortlisting aid, 2026-08-14: Context.dev's Brand Data/Styleguide endpoint can auto-fetch a candidate guide for a human to review — stays a shortlist for a curator to generalize, same discipline as the skills.sh sweep, not an automatic recipe (non-negotiable #4).
2. **Hand-authored**, where no public guide fits a variant.
3. **Tastefield's own future live-URL scan** (see open question above) — once `src/scan/` can extract from a live site, not just a repo.
4. **Refero's DESIGN.md catalog, pulled and substantially reworked.** Token values (colors, spacing, type) can be pulled from styles.refero.design as raw material for a variant, then modified enough to be genuinely distinct — not just relabeled — before it ships. Curation of which entries get pulled is manual, per non-negotiable #4.

**Reconsidered 2026-08-13.** This lane was originally ruled out entirely (see below) — decision was to proceed anyway, with two conditions: the rework has to be substantial enough that the result is actually distinct, not relabeled, and Refero's robots.txt / terms of service need an actual check before scraping anything (not yet done as of this note). If either condition slips, this reverts to the original exclusion.

Original concern, kept for context: Refero's catalog is their curated work product, not an original source, and reusing it risks reopening the "extraction gallery" problem already ruled out for Tastefield generally (see `extract-design-system` in Registry facts) — a "start from theirs, then tweak" framing doesn't remove that concern, it just adds a step before it applies. Refero remains fine to browse for calibration regardless of this decision — what actually makes two fintech products feel distinct.

**Two install paths, not one (decided 2026-08-14).** Confirmed directly against skills.sh Packs: `npx @tastefield/mcp --recipe=fintech-trust-first/neobank` is the named, browsable, published path (see naming above). Alongside it, an opaque share-link path (`npx skills add https://tastefield.sh/p/<id>`, matching Packs' own `npx skills add <url>`) for sharing a draft or unlisted recipe informally — no discovery, no name required, before it's ready to be a published category variant.

## Bugs already found and fixed — don't reintroduce

- **cva class strings contain colons.** `ghost: "hover:bg-muted"` — a naive parser reads `hover:` as a variant key. The parser is string-literal aware.
- **tsconfig is JSONC.** Comments and trailing commas mean `JSON.parse` fails. Alias reading uses a targeted regex.
- **Plurals.** `review-animations` didn't match `animation`. Term matching allows an optional trailing `s`.
- **Multi-word terms vs. hyphenated slugs.** `"design system"` never matched `design-system`. Haystacks are normalised (`-_/` → space) before matching.
- **Domain floor was above single-summary-match weight.** A skill described as "popup design and copy" reported neither domain. Floor is 6, summary match is 8.
- **Merging leaderboard views.** `trending` and `hot` report *windowed rates* in the same `installs` field as cumulative. Merging naively overwrites 770,700 with 4,100.
- **OIDC tokens rotate ~12h.** A stored `VERCEL_OIDC_TOKEN` secret dies before the next 3-day cron run. CI mints a fresh one from a long-lived `VERCEL_TOKEN`.

- **Closest product-shape overlaps found — buildwithtaste.com and tasteprofile.io (2026-08-15).** buildwithtaste.com: screenshot-capture a personal library of admired UI, AI extracts a style profile, synced via SKILL.md + MCP into Cursor/Claude Code/Codex — and a live, working "rent a designer's taste" marketplace (named creators, real pay-to-plug-in). Same gap as Context7, Design Arena, and Adobe, now confirmed a fourth time.

**Addressable-market boundary, surfaced by their $999 "Brand Discovery Workshop" add-on (2026-08-15).** That add-on exists because some of their clients don't have a brand yet — a human facilitates one into existence from nothing. Tastefield's whole pipeline assumes the opposite: scan an *existing* repo, compile what's *actually there*. A pre-brand founder with nothing to scan isn't served by that architecture at all today. Not a gap to fix now — a boundary worth stating plainly: addressable market is companies with a real, existing system, not companies that need one invented.

**Differentiation, sharpened against Adobe's learning mechanic (2026-08-14):** the "learns from rejection/approval over time" idea is worth taking, but not the way Adobe implements it — their brand brain is a proprietary, opaque model; nothing about *why* it scored something a certain way is auditable or portable. Tastefield's version of the same idea should stay inside its own existing discipline: when a creative director (or dev lead) rejects an agent's output and says why, that correction becomes a candidate negative restraint — reviewed and promoted by hand, per non-negotiable #4, not silently absorbed into a black box. Same underlying capability Adobe has, but the output is an explicit, versioned, checkable rule instead of an opaque model update — consistent with "a rule an agent merely reads is advisory; a rule that can be verified is enforcement" (Architecture, above).

- **Skill-eval tooling — skilltune.dev (2026-08-15).** Real, live, priced ($24.99/mo web-only, $149/yr founder tier w/ CLI + local execution). Different axis than `check_compliance`, not a competitor to it: skilltune tunes a SKILL.md's *prose* — an LLM-judged score, iterated version by version, against synthetic eval cases the lab itself generates from a description. `check_compliance` verifies *output* against deterministic, company-specific, regex-checkable rules compiled from real tokens. Soft general-purpose instruction tuning vs. hard verified enforcement — the "advisory vs. verified" line already drawn in Architecture, not a case that needs re-litigating. What's actually worth taking is the eval discipline, not the product: eval cases locked immutable before any tuning starts, every version scored, benchmarked against an untouched baseline. Directly applicable to the still-open benchmark gap below.

"Design visual" is already one of eleven listed categories, alongside marketing growth, creative production, security, and others — a real, general-purpose, at-scale distribution channel with a design slot already existing independently of anything Tastefield builds, mechanically usable from Claude Code or any @skills-compatible client today.

Second, their roadmap lists a "Local Domain Model — single source of truth for intent across your project," escalating to a Central Domain Model across a team. Close enough to compiled brand rules to track deliberately rather than dismiss.

  **Differentiation holds, and it is the same line already drawn five times in this section.** Blume proposes a rule in prose for a human to approve; nothing afterwards verifies the agent actually followed it. They improve what goes *in* to generation. `check_compliance` checks what comes *out*. Advisory versus verified, now confirmed against Context7, skilltune, Design Arena, Adobe, Taste Profile and Blume — six independent products, none carrying an enforcement engine. Worth reading as evidence the enforcement half is genuinely the defensible one, not as reassurance to stop checking.

  **What's worth taking is presentation, not product.** Their roadmap renders in three visible tiers — shipped features unbadged, `Soon` badges inline on the same list, and a separate "On the horizon" section carrying `Next` — under a heading that states the quiet part directly: "Today, and the corners of the agent setup we're building toward." Directly applicable to the two standing honesty problems here: a domain axis where only Visual genuinely ships, and a registry that isn't built. - **Individually-authored checker skills — Carl Sziebert's ux-agent-skills (2026-08-18, via LinkedIn/GitHub).** A solo practitioner (Head of UX Engineering, Google Cloud) shipping five MIT-licensed Claude/agent skills — `/ux-spec`, `/usability-audit`, `/cuj-audit`, `/ux-audit`, `/ux-review` — that author Critical User Journeys, run expert heuristic evaluation, replay journeys against a running app, and roll everything up into one schema'd go/no-go report. Worth tracking precisely, not dismissing as another free skill dump: `/cuj-audit` replays against a *live running app* and reports the exact step that broke — closer to the verified side of the advisory-vs-verified line than any of the six products already found lacking an enforcement engine (Context7, skilltune, Design Arena, Adobe, Taste Profile, Blume, listed above). The extensible report schema — "any auditor that emits the schema joins the roll-up without touching the orchestrator" — is the same registry-of-checkable-things shape as the Taste Arena, just for UX audits instead of design tokens.

  **Structural reason this doesn't monetize the same way Tastefield's own x402 idea assumes, 2026-08-18.** The skill files execute inside the *buyer's* own agent (Claude Code/Cursor), on the buyer's own compute — there's no server of his anywhere in that flow. That's the concrete, non-hypothetical version of the tension already flagged against Tastefield's own Hosted Recipe API question (see Open questions, above): x402 needs a server the agent pays to call, and "clone a skill file and run it locally" has no server to attach a meter to. The free giveaway itself isn't a monetization failure — for an individual with real pedigree, it reads as the same credibility/recruiting play already named for companies publishing open design systems (Roadmap reframe, "why anyone actually submits," above) — but turning it into x402 revenue would require a second, separate surface: a hosted version of the roll-up execution, kept distinct from the free, auditable skill definitions, not a paywall bolted onto the existing repo.

## What is NOT done

- **The benchmark has only been run once, synthetically.** 2026-08-13: 8 tasks, both arms hand-authored by the same coding agent (not two independent live agent sessions) against `test/fixtures/sample-app`. Baseline density 31.21 (49 errors / 5 warnings over 173 lines); governed density 0. Full output in `bench-runs/RESULTS.txt`. This proves the harness and checker work end-to-end on realistic code — it does **not** yet prove the claim against real prompt variance, since one author wrote both arms with full knowledge of what each arm was supposed to demonstrate. The still-open, higher-value version: collect governed/baseline generations from two actual agent sessions (e.g. Claude Code with vs. without the Tastefield MCP server wired in) and re-run `node dist/bench/run.js` unchanged against those. Discipline to borrow from skilltune.dev (see Competitive landscape), 2026-08-15: lock the task set immutable before running either arm, the same way their eval cases are locked before tuning starts — removes any possibility the task selection itself was shaped by knowing which arm needed to win.
- **The MCP server has never been verified against a real IDE.** The protocol handshake is smoke-tested with a real MCP client over stdio, which proves the plumbing — not that it changes what Cursor writes.
- Only the Phase 1 core engine is built. Phase 1's public registry, Phase 2 (Studio: landing page, and the "Parametric Tweaker" GUI referenced in strategy docs), and Phase 3 (agency workspace, CI/CD PR bot) are all unstarted. Strategy docs describe the Tweaker in present tense; it doesn't exist yet.
- Pricing ($99–299/mo agency, $10k–30k/yr enterprise) is unvalidated — no prospect conversations behind those numbers.
